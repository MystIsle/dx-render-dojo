# 코딩 규약

기준 시점 : 2026-09-27

dx-render-dojo 의 C++ 코드 규약입니다. 코드를 쓰다가 걸리는 주제의 절만 찾아 읽으면 됩니다. 규약을 바꿀 때는 이 문서를 고칩니다.

이 문서에서 "원문"은 Rastertek DirectX 11 튜토리얼의 코드를 가리킵니다.

서식은 `.clang-format`, 네이밍은 `.clang-tidy` 로 검사합니다. 도구가 잡지 못하는 항목은 사람이 지킵니다.

규칙은 두 종류입니다. 이름 모양과 서식(6절의 접두·대소문자, 8절)은 표기 규칙이라 예외 없이 따릅니다. 나머지는 설계 규칙이라 대상과 이유를 함께 적고, 이유가 해당하지 않는 코드에는 적용하지 않습니다.

구조는 이 순서로 정합니다.

1. 무엇을 만들지 : 1절
2. 만들기로 한 것의 클래스 경계, 파일 나눔, 함수가 맡는 일 : 기준 구현(DirectXTK, MS D3D11 샘플). 근거로 들 때는 파일이나 함수 이름을 적음
3. 기준 구현에 해당하는 구조가 없을 때 : 가장 단순한 모양

원문에서는 그 편이 무엇을 그리는지만 가져옵니다.

## 1. 추상화

구조는 기법이 요구할 때 생깁니다. 미리 만드는 것은 도구와 뼈대뿐입니다.

- 현재 튜토리얼이 요구하지 않는 추상화(새 클래스·인터페이스·간접 층)는 만들지 않음. 선언을 알맞은 곳으로 옮기거나 함수를 나누는 것은 추상화가 아님
- 예외 : 아래 둘을 모두 만족하면 미리 넣음
  - 확실성 : 교재 진행이나 자체 렌더러가 요구함. "쓸 것 같다" 는 해당 없음
  - 비용 역전 : 나중에 넣는 비용이 지금보다 크게 높음. 태그 diff 가 그대로 교재 코드가 되므로 구조 변경은 뒤 편일수록 비쌈
- 예외로 미리 넣은 것 : 공통 도구(로그, 체크 매크로, 싱글톤 틀), 프레임 구조(`Update`/`Render` 분리), 실행 파일 기준 경로(`FPaths`)
- 예외가 아닌 것 : 백엔드 추상화(RHI), 렌더 그래프, 셰이더 공통 베이스. 요구되는 편에서 만듦
- 중복 : 비슷한 코드의 중복은 3번째에서 뽑음. 같은 사실을 두 곳에 적은 중복은 아래 짝 선언을 따름
- 짝을 맞춰야 하는 선언 : 한쪽이 다른 쪽을 참조하게 둠. 입력 요소 배열은 정점 구조체 안(`FVertexPositionColor::InputElements`), 셰이더 단계 사이 구조체는 한 `.hlsl` 안. 언어가 달라 참조할 수 없는 짝(C++ 상수 버퍼 구조체와 `cbuffer`)만 주석으로 잇고 크기를 `static_assert` 로 검사함. 한쪽만 고쳐도 빌드는 되고 결과만 틀어지므로 3번째를 기다리지 않음

## 2. 소유

- COM 객체 : `ComPtr<T>`
  - 주소를 넘길 때 `&` 를 쓰지 않음. `ComPtr` 의 `&` 는 들고 있던 객체를 먼저 놓는 동작이 숨어 있음
  - 받아 오는 출력(Create·Get·`IID_PPV_ARGS`) : `.ReleaseAndGetAddressOf()`. 다시 만들어 받아도 옛 객체가 새지 않음
  - 넘겨 주는 입력(Set 계열의 배열 인자) : `.GetAddressOf()`
  - 다른 인터페이스로 넓힐 때 : `As(&Other)`. `As` 는 이 모양으로만 받는 유일한 예외. 날 포인터밖에 없을 때만 `QueryInterface(IID_PPV_ARGS(...))`
- 내 객체 : 값 멤버가 기본. 다형성이 필요할 때, 다시 만들어야 할 때, 생성을 늦춰야 할 때만 `std::unique_ptr<T>`
- `shared_ptr` : 쓰지 않음
- raw 포인터·참조 : 빌리는 매개변수와, 감싼 대상을 빌려주는 게터의 반환값(`GetDevice`)에만
- 소유자가 가진 것 : 빌리는 매개변수로 받음(앱이 입력을 쓰면 `Update(const FInput& Input)`). 싱글톤 `Get()` 으로 소유자에게 거슬러 올라가 멤버를 꺼내지 않음. 받는 쪽의 의존이 선언에 드러나야 함
- `new` / `delete` : 직접 호출 금지

해제는 값 멤버의 소멸자와 `ComPtr`·`std::unique_ptr` 가 맡습니다. 그래서 `Shutdown` 계열 함수와 `SafeRelease` 는 쓰지 않습니다.
창·디스플레이 설정처럼 스마트 포인터가 맡지 못하는 자원은 소멸자에서 돌려놓습니다.

**싱글톤 수명**

- `Get()` 은 인스턴스가 없으면 만듦. 대부분의 싱글톤은 이것만으로 충분함
- 생성 비용이 크거나 생성 시점을 잡아야 하면 `Prepare()` 로 앞당김. `FSystem` 이 여기에 해당함
- 해제 시점이 중요한 싱글톤만 `Release()` 를 부름. 그 밖은 프로세스 종료에 맡김
- `Shutdown` 계열 은퇴의 예외는 이 `Prepare`·`Release` 둘뿐임

## 3. 초기화

- 멤버 : 헤더에서 기본 초기화
- 생성자·소멸자 : 필요할 때만. 본문이 빈 생성자·소멸자는 쓰지 않음
- 복사 : 핸들을 쥐거나 `this` 를 밖에 등록하는 클래스만 `= delete`(예 : `FWindow`, `FD3D11Graphics`). 이때 기본 생성자가 사라지므로 `= default` 로 한 줄 적음. 베이스가 이미 막았으면 파생에는 적지 않음. 나머지 클래스는 특수 멤버를 적지 않아 복사·이동이 그대로 됨. `ComPtr` 멤버는 복사하면 참조 카운트가 늘 뿐이라 막을 이유가 되지 않음
- `Initialize` : 창·디바이스·버퍼처럼 바깥 자원을 만들거나 먼저 준비된 객체를 받아야 하는 클래스에만 둠. 값만 가진 클래스(`FCamera`)는 기본 초기화와 세터로 끝냄. 실패를 호출자에게 넘기면 `bool Initialize()`, 그 자리에서 멈추면(`CHECK_FATAL`) `void Initialize()`
- 위임 : `Initialize` 가 함수 하나에 일을 통째로 넘기는 위임(`Initialize` → `InitializeShader`) 금지. 이름만 늘고 읽을 곳이 둘이 됨. 단계가 여럿이면 하는 일을 이름으로 단 함수로 나눠도 됨(`CreateDevice`, `CreateSwapChain`)

## 4. 에러

- 실패 검사는 두 매크로로 함
  - `CHECK_FATAL(expr)` : 계속할 수 없는 실패. 그 자리에서 로그 → 상자 → 종료 코드 1. 디버거가 붙어 있으면 그 줄에서 먼저 멈춤
  - `CHECK_RETURN(expr, false)` : 호출자에게 넘기는 실패. 로그를 남기고 반환
- 복구하는 실패(대체 경로가 있는 것)는 매크로로 검사하지 않고 `if` 로 직접 적음 (`if (SUCCEEDED(...))`). 매크로는 실패를 에러로 로그에 남김
- `if (FAILED(hr)) return false;` : 금지
- 두 매크로는 `HRESULT`·`bool`·포인터만 받음. 그 밖의 반환값은 성공 조건을 비교식으로 적음 (`RegisterClassExW(...) != 0`)
- `long` 을 돌려주는 함수(`LSTATUS` 를 돌려주는 `Reg*` 등)도 비교식으로 적음. `HRESULT` 가 `long` 이라 매크로가 받아 버리고, 양수 에러 코드를 성공으로 읽음
- `HRESULT` 가 실패하면 로그에 그 값이 함께 찍힘

`BOOL`·`ATOM` 을 받는 오버로드는 두지 않습니다. `int` 오버로드가 생기면 0 이 성공인 `errno_t`(`fopen_s` 등)의 판정이 뒤집히고, `short`·범위 없는 `enum` 을 넘겼을 때 나던 컴파일 에러도 사라집니다.

## 5. 문자열·배열

- 경로 : `std::filesystem::path` 또는 `const wchar_t*`
- 보관 : `std::wstring`
- const 가 아닌 `char*` : 금지
- API 가 주는 `char*` 를 넓힐 때 : `MultiByteToWideChar`. 코드 페이지를 모르면 `CP_ACP`. 바이트째 복사(`std::wstring(Text.begin(), Text.end())`) 금지. 한 바이트를 한 글자로 옮기면 한글이 깨짐
- 고정 길이 배열 : `std::array`. C 배열은 쓰지 않음. API 에는 `.data()` 와 `.size()` 로 넘김. 크기가 타입에 붙어 개수를 따로 적지 않아도 됨

## 6. 네이밍

언리얼 컨벤션을 전면 채택합니다.

| 대상 | 접두 |
|---|---|
| 클래스·구조체·공용체 | `F` |
| 인터페이스 (순수 가상 함수만 있는 클래스) | `I` |
| 추상 클래스 | `A` |
| 템플릿 | `T` |
| enum | `E` |
| bool 변수 | `b` |

- 멤버·로컬·매개변수·함수·파일 : 모두 PascalCase
- 열거자·네임스페이스·타입 별칭·템플릿 매개변수 : PascalCase. 타입 별칭과 템플릿 타입 매개변수는 가리키는 타입에 맞춰 `F`·`T`·`E` 를 붙여도 됨 (`template <typename T>`)
- 매크로 : 대문자와 밑줄 (`CHECK_FATAL`)
- 파일 이름 : 접두까지 클래스 이름과 같게 (`FModel` → `FModel.h`, `FModel.cpp`)
- 셰이더 파일 : 효과 하나에 `.hlsl` 하나(`Color.hlsl`). 정점·픽셀 진입점을 같은 파일에 둠. 단계 사이 구조체를 한 번만 적으려는 것
- `On` 접두 : 남에게 등록되어 불리는 콜백 함수에만. 예 : `FSystem::OnResize` 는 `FWindow` 에 등록되는 콜백, `FWindow::HandleMessage` 는 `WndProc` 가 직접 부르는 함수
- `Render`·`Draw`·`Bind` : `Render`·`Draw` 는 그리기 호출(`Draw*`)까지 이어짐. 상태만 묶는 함수는 `Bind`, 물체마다 바뀌는 상수를 채우는 함수는 `Set*`(`SetMatrices`). 그리기 호출은 정점·인덱스 수를 가진 쪽이 함. 이름만 보고 무엇이 그리는지 알 수 있게 하려는 것

Rider 이름 규칙(`DxRenderDojo.sln.DotSettings`)은 이 절을 옮긴 것입니다. 바꿀 때는 이 절을 먼저 고치고, Rider 설정 › 에디터 › 코드 스타일 › C/C++ › 이름 지정 탭에서 맞춘 뒤 "솔루션 팀 공유" 로 저장합니다. 키가 GUID 라 파일을 손으로 고치지 않습니다.

`.clang-tidy` 가 잡지 못해 사람이 확인하는 것

- 파일 이름
- `T` 는 템플릿에만. 도구는 `T` 로 시작하는 클래스 이름을 검사하지 않음
- `I` 는 순수 가상 함수만 있는 클래스에만. 도구는 추상 클래스 중 `I` 로 시작하는 이름을 검사하지 않음
- bool 변수의 `b`. 도구는 `b` 로 시작하는 이름을 검사하지 않을 뿐, 그 변수가 bool 인지는 보지 않음
- `!` 대신 `== false` (8절). 도구가 검사하지 않음
- `On` 접두는 콜백에만. 도구가 검사하지 않음
- `Render`·`Draw`·`Bind` 가 하는 일. 도구가 검사하지 않음
- 선언 순서 (7절). 도구가 검사하지 않음
- include 방향 (7절). 도구가 검사하지 않음

## 7. 헤더

- `#pragma once` 사용
- 매개변수 이름 : 항상 표기
- 값으로 받는 매개변수 : `const` 를 붙이지 않음. 호출하는 쪽에는 차이가 없음. 참조·포인터로 받을 때만 가리키는 대상에 `const` (`const FWindow& Window`)
- DirectXMath 인자 : 행렬·벡터를 받거나 돌려주는 함수는 선언과 정의에 `XM_CALLCONV` 를 붙임. 행렬은 첫째 `FXMMATRIX`, 나머지 `CXMMATRIX`. 벡터는 1~3번째 `FXMVECTOR`, 4번째 `GXMVECTOR`, 5·6번째 `HXMVECTOR`, 나머지 `CXMVECTOR`. 별칭에 `const` 와 `&` 가 들어 있어 덧붙이지 않음. 인자를 SIMD 레지스터로 넘기는 MS 관례(DirectXMath 문서 "Library Internals"). 생성자는 예외로 `XM_CALLCONV` 없이 행렬을 `CXMMATRIX` 로 받음
- DirectXMath 멤버 : 계산에 쓰는 행렬·벡터는 `XMFLOAT4X4`·`XMFLOAT3` 같은 저장 타입으로 들고, `XMLoad*`·`XMStore*` 로 지역 `XMMATRIX`·`XMVECTOR` 와 오감. 정렬을 따지지 않고 크기가 작음(DirectXMath 문서 "Getting started")
- 한 줄 게터 : 인라인 `const`
- `using namespace` : 헤더에서 금지
- 전역 상수 : 두지 않음. 한 함수만 쓰면 그 함수 안의 `constexpr`, 여러 함수가 쓰면 클래스의 `static constexpr` 나 멤버로. 시작 설정(창 크기, 전체 화면, VSync)은 상수로 보지 않음. 만드는 쪽이 채워 `Initialize` 인자로 넘기고, 받는 쪽은 계속 쓰는 값만 멤버로 둠. 같은 상태를 두 곳에 두면 한쪽이 낡음
- 클래스 안 상수 : `static constexpr`. `static` 없는 `const` 멤버 변수는 객체마다 값이 다를 때만
- include 경로 : `Source/` 기준으로 폴더까지 적음(`#include "Core/FSystem.h"`). 짝 헤더와 같은 폴더·하위 폴더의 헤더도 같음. 언리얼 엔진 코드와 에디터의 새 클래스 마법사가 모듈의 `Public` 루트 기준으로 적는 것과 같은 방식
- include 방향 : 소유되는 쪽은 소유자 헤더를 include 하지 않음(`App` 이 `Core/FSystem.h` 를). Graphics·Shaders·Utility 는 Core·App 을 include 하지 않음. 아래층에 넘길 것은 위층 타입 대신 기본 값(`HWND`, 크기, `bool`)으로. 층이 거꾸로 이어지면 한쪽만 떼어 읽거나 시험할 수 없음
- 접근자 : 읽는 쪽이 생길 때 만듦. 멤버를 더했다고 게터를 같이 만들지 않음. 예외는 클래스가 감싼 대상 자체를 꺼내는 접근자(`FWindow::GetHandle` 의 `HWND`). 래퍼는 그것을 내주려고 있으므로 읽는 쪽보다 먼저 둬도 됨. 그 밖에 쓰이지 않는 접근자는 죽은 코드
- 주석 : 지금 코드에 대해 계속 참인 문장으로 씀. 뒤 편의 계획이나 뒤 단계에서 생길 이름을 담지 않음. 구조가 바뀌면 그 편에서 주석도 고침

**선언 순서**

static 을 먼저, 함수를 변수보다 먼저 둡니다. `.cpp` 의 정의 순서도 헤더의 선언 순서를 따릅니다.

1. static 묶음 : 상수·함수·변수 각각 안에서 접근 구역은 public → protected → private
   - `static constexpr` 상수
   - static 함수 : 아래 함수 순서대로
   - static 변수
2. static 아닌 것 : 접근 구역은 public → protected → private
   - 구역 맨 앞 : 중첩 타입·별칭
   - 함수 : 생성·소멸 → 초기화 → 게터 → 세터 → 가상 → 일반 → 콜백
   - private 끝 : 변수. 생성은 선언 순서, 소멸은 그 역순이라 다른 멤버를 쓰는 멤버를 뒤에 둠(창을 쓰는 멤버는 `FWindow` 뒤). 생성자가 일하지 않는 클래스에서 실제로 걸리는 것은 소멸 순서

- 생성·소멸 : 기본 생성자, 복사 `= delete`, 소멸자
- 초기화 : `Initialize` 와 수명 함수(`Prepare`·`Release`). 만든 직후 한 번 부르는 것만. 크기 변경처럼 일이 생길 때 다시 부르는 함수(`Resize`)는 일반 함수
- 콜백 : 남에게 등록해 불리게 하는 함수. 이름이 `On` 으로 시작함(6절). 콜백 안에서 직접 부르는 처리 함수(`HandleMessage`)는 일반 함수
- 함수가 `const`·`constexpr` 인지는 순서에 영향 없음. 하는 일로 나눔
- 빈 줄 : 묶음 사이에 하나. 같은 묶음 안의 빈 줄은 쓰는 사람이 정함

## 8. 서식

- 중괄호 : Allman
- 들여쓰기 : 탭
- 줄 길이 : 120자 상한
- 부정 : `== false` 로 적음. `!` 는 삼항 연산자 안처럼 줄 길이가 빠듯할 때만
- void 함수 끝 `return;` : 쓰지 않음
- 블록 뒤 빈 줄 2개 : 두지 않음
- 120자를 넘는 인자·매개변수 목록 : 한 줄에 하나씩
- 접근 지정자 : 들여쓰지 않음 (`public:` 을 `class` 와 같은 열에)
- 네임스페이스 : 안쪽을 들여씀 (`NamespaceIndentation: All`)
- 포인터·참조 : `*` 와 `&` 를 타입에 붙임 (`const wchar_t* Name`, `const FWindow& Window`)
- 그 밖의 서식 : Microsoft 스타일 기본값

120자 상한은 학습 노트 때문입니다. 노트의 코드 블록은 가로 스크롤 대신 자동 줄바꿈되므로 긴 줄은 읽기가 깨집니다.

## 9. 기각안

규칙을 바꾸자는 안이 여기 있으면 이유를 먼저 봅니다. 규칙이 언제, 왜 바뀌었는지는 `docs/CODING_STYLE_HISTORY.md` 에 있습니다.

- `m_camel` : 번거로움
- `_Upper` : 예약어
- `CHECK_RETURN` 의 `BOOL`·`ATOM` 오버로드 : 4절 참고
- 원문 이름과 새 이름의 대응 표 : 클래스를 나누면 원문과 대응되지 않음
- 첫 실패 이유를 기억했다가 `wWinMain` 에서 상자로 띄우기 : 스택이 풀린 뒤라 디버깅에 불리하고, 이유를 나르는 장치가 따로 필요함
- 게터를 public 맨 끝에 두는 선언 순서 : 둘 다 이치가 있어 오래 써 온 기조(7절)를 따름
- 짝 헤더나 같은 폴더 헤더만 파일 이름으로 include : 한 헤더가 두 이름을 갖고, 폴더를 옮기면 양쪽 모양을 다 고쳐야 함. 하위 폴더를 모두 검색 경로에 넣으면 이름이 같은 파일이 부딪힘
- 규칙마다 목적·대상·예외 칸을 두는 표 : 모든 규칙이 세 줄 이상이 되고, 표기 규칙까지 칸을 채우면 소음

**보류**

- `new` 금지의 예외(private 생성자와 `std::unique_ptr<T>(new T())`) : 싱글톤의 유일성을 컴파일러가 지키게 할 수 있음. 싱글톤 기조와 함께 다룸

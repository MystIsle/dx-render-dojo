# 코딩 규약 변경 이력

`docs/CODING_STYLE.md` 의 규칙이 언제, 왜 바뀌었는지 적습니다. 규칙 본문과 기각안은 그 문서에 있습니다. 새 항목은 맨 아래에 덧붙입니다.

**언리얼식 네이밍 채택 (2026-09-13)**

2026-08-23 에는 "멤버/로컬 구분이 약함" 을 이유로 기각했습니다. 2026-09-13 에 아래 이유로 채택했고, 구분이 약한 문제는 감수합니다.

- 스터디원이 언리얼 트랙 출신이라 접두 어휘가 독자에게 익숙함
- 회사 UE5 코드와 표기가 같아져 손에 익은 대로 쓸 수 있음

**`CODING_STYLE.md` 로 옮기면서 정한 것 (2026-09-13)**

- 파일 이름에 접두 포함
- 추상 클래스 접두 `A` 추가. 인터페이스 `I` 는 순수 가상 함수만 있는 클래스로 한정
- `Shutdown` 계열도 `SafeRelease` 와 함께 은퇴
- 원문 이름과 새 이름의 대응 표는 두지 않음. 클래스를 분리하면 원문과 대응되지 않는 경우가 있기 때문. 필요해지면 참고용으로 `CODING_STYLE.md` 위나 아래에 추가

**02편을 쓰면서 정한 것 (2026-09-13)**

- 생성자·소멸자는 필요할 때만. 창처럼 스마트 포인터가 맡지 못하는 자원은 소멸자에서 정리
- 전역 상수 금지. 쓰는 클래스의 `static constexpr` 나 멤버로
- `CHECK_RETURN` 은 `HRESULT`·`bool`·포인터만. 그 밖의 반환값은 비교식
- static 멤버는 클래스 맨 위
- 접근 지정자는 들여쓰지 않음

**02편 설계 수정 (2026-09-20)**

근거는 2026-09-20 조사 세션입니다. DirectXTK 템플릿·hw3d·learnd3d11·Godot·Unreal 을 대조했습니다.

- 소유는 값 멤버가 기본. 참고한 코드베이스가 모두 값 멤버를 기본으로 쓰고, `unique_ptr` 는 다형성·재생성·지연 생성일 때만 씁니다
- 1절 추상화에 예외 두 조건(확실성·비용 역전)을 넣었습니다. 태그 diff 가 그대로 교재 코드가 되어, 구조를 뒤 편에서 바꾸는 비용이 크기 때문입니다
- 3절 복사 금지에 "베이스가 이미 막았으면 파생에는 적지 않음" 을 넣었습니다. 베이스가 복사를 `= delete` 하면 파생의 복사는 컴파일러가 자동으로 delete 하고, 파생이 생성자를 선언하지 않았으므로 기본 생성자도 그대로 남습니다. `TSingleton` 을 상속하는 `FSystem`·`FLog` 가 여기에 해당합니다

**02편 코드 리뷰 (2026-09-20)**

- 2절에 싱글톤 수명 항목을 넣었습니다. 그 전에는 `wWinMain` 이 객체를 값으로 들고 `TSingleton` 은 포인터만 등록했는데, 싱글톤이라는 이름과 "밖에서 만들고 소유한다" 는 실체가 어긋났습니다. 이제 `TSingleton` 이 `static std::unique_ptr` 로 소유합니다
- 8절에 부정 표기를 넣었습니다. `!` 는 한 글자라 훑어 읽을 때 놓치기 쉽습니다
- 7절 전역 상수에 "한 함수만 쓰면 그 함수 안의 `constexpr`" 을 앞에 넣었습니다. 범위가 좁은 쪽을 먼저 적은 것이고 취지는 그대로입니다

**03편 설계 (2026-09-23)**

- 4절에 `CHECK_FATAL` 을 넣었습니다. 계속할 수 없는 실패는 발견한 자리에서 멈춥니다. 초기화 실패를 `wWinMain` 까지 올리던 구조에서는 상자에 가장 바깥 검사만 떴고, 초기화 실패 경로가 `FSystem::Release` 를 거치지 않았습니다
- 기각 : 첫 실패 이유를 기억했다가 `wWinMain` 에서 상자로 띄우는 안. 스택이 풀린 뒤라 디버깅에 불리하고, 이유를 나르는 장치가 따로 필요합니다
- 3절 `bool Initialize` 를 "실패를 호출자에게 넘기는 초기화만" 으로 좁혔습니다. `FWindow`·`FSystem`·`FD3D11Graphics` 의 `Initialize` 는 `void` 입니다
- 4절에 복구하는 실패는 `if` 로 적는다는 줄과 `long` 반환 함수 줄을 넣었습니다
- 치명 실패로 끝나기 직전에 D3D·DXGI 디버그 메시지를 로그로 내보내려고 `Return::SetFatalHook` 을 두었습니다. 원인을 설명하는 메시지는 실패 직전에 쌓이는데, 그 자리에서 끝나면 메시지를 비울 차례가 오지 않습니다

**04편 설계 (2026-09-24)**

- 1절 예외 목록에 `FPaths` 를 넣었습니다. 셰이더를 exe 옆에서 읽으려고 04편에 만들었고, 05편 텍스처도 같은 함수를 씁니다
- 공통 도구는 `Source/Utility/` 에 모읍니다. `Check`·`FLog`·`TSingleton` 은 02편부터 여기에 둡니다. 처음에는 04편에서 `Core` 에서 옮겼는데, 2026-09-25 이력을 다시 써서 02편부터 두었습니다

**선언 순서 (2026-09-25)**

- 7절에 선언 순서를 넣었습니다. 그 전에는 "static 멤버는 맨 위" 뿐이었고, 03·04편 코드는 게터를 public 맨 끝에 두는 모양으로 굳어 있었습니다
- 순서는 조은님이 전부터 쓰던 기조(생성·소멸 → 초기화 → 게터·세터 → 가상 → 일반 → 콜백)에 static 우선과 함수 → 변수를 더했습니다
- 6절에 `On` 접두를 콜백 전용으로 넣었습니다. 순서의 콜백 묶음을 이름으로 판정합니다
- 기각 : 게터를 public 맨 끝에 두는 모양. 둘 다 이치가 있어 오래 써 온 기조를 따릅니다
- 적용 : 이력 전체를 다시 써서 02편 첫 코드 커밋부터 새 순서로 맞췄습니다. 0단계 커밋까지만 해시가 그대로이고 `tut01` 부터는 모두 바뀌었습니다. 이 날 전에 적어 둔 `tut01` 과 그 뒤 커밋의 해시는 옛 이력을 가리킵니다

**Rider 이름 규칙 (2026-09-25)**

- Rider 기본 이름 규칙은 STL 방식(snake_case)이라 PascalCase 이름마다 점선 힌트가 떴습니다. 6절을 옮긴 `DxRenderDojo.sln.DotSettings` 를 넣었습니다
- 옮기면서 6절에 없던 항목(열거자·네임스페이스·타입 별칭·템플릿 매개변수·공용체·매크로)을 더했습니다
- 같은 항목을 `.clang-tidy` 에도 더했습니다
- 설정 파일(DotSettings, `.editorconfig`·`.gitattributes` 줄, `.clang-tidy` 항목)은 이력을 다시 써서 `tut01` 커밋부터 넣었습니다. 태그에서 브랜치를 따도 Rider 설정이 따라갑니다
- 7절에 값 매개변수의 `const` 를 넣었습니다. Rider 가 값 매개변수마다 "상수로 만들 수 있다" 는 약한 경고를 띄웠습니다(02편 코드에서 30곳쯤). 붙이지 않기로 하고 DotSettings 에서 그 검사(`CppParameterMayBeConst`)를 껐습니다

**include·접근자·주석 (2026-09-25)**

- 7절에 include 경로를 옮겼습니다. 전에는 CLAUDE.md 에 "include 는 항상 폴더까지" 한 줄만 있었습니다. 짝 헤더만 파일 이름으로 적자는 안을 검토했고, 언리얼 엔진(`Private/Components/ActorComponent.cpp` 의 `#include "Components/ActorComponent.h"`)과 에디터 새 클래스 마법사(`GameProjectUtils` 가 옛 `#include "클래스.h"` 를 지우고 폴더를 포함한 경로로 바꿈)를 확인해 지금 규칙을 유지했습니다. UBT 는 `BuildSettingsVersion` V2 부터 `Public` 루트 기준입니다
- 기각 : 짝 헤더나 같은 폴더 헤더만 파일 이름으로. 한 헤더가 두 이름을 갖게 되고, 폴더를 옮기면 양쪽 모양을 다 고쳐야 합니다. 게임 템플릿처럼 하위 폴더를 모두 검색 경로에 넣으면 이름이 같은 파일이 부딪힙니다
- 7절에 접근자와 주석을 넣었습니다. 읽기 검토에서 02편 `FWindow::GetHandle`(03편에서 처음 씀)과 `FSystem::GetWindow`(쓰는 곳 없음), 02편 `FSystem.h` 의 "디바이스를 갖게 될 `FApplication`"(03편은 `FD3D11Graphics` 가 가짐)이 나왔습니다. 주석은 "창을 쓰는 멤버는 `FWindow` 뒤에 둔다" 로 바꿔 02편 5단계부터 이력에 반영했습니다. 03편 1단계에서 주석을 고치던 줄은 없어졌습니다
- 02편 `Main.cpp` 주석의 "창과 디바이스를" 도 같은 까닭으로 고쳤습니다(2026-09-26). 02편에는 디바이스가 없습니다. 같은 자리에 `FLog::Prepare()` 를 넣어 로그 콘솔을 창보다 먼저 엽니다. 늦게 열린 콘솔이 맨 앞에 와서 창을 누르기 전까지 키 입력을 가져갔습니다
- 접근자에 예외 하나를 두었습니다(2026-09-26). 필요할 때 만드는 것이 기본이지만 뻔히 있어야 할 것은 미리 둬도 된다는 조은님 의견을 따랐습니다. "뻔하다" 는 사람마다 달리 읽혀서 판별 기준을 "클래스가 감싼 대상 자체를 꺼내는가" 로 적었습니다. 창을 감싼 `FWindow` 의 `GetHandle` 은 여기에 들어 02편에 남겼습니다. `FSystem` 은 창을 감싼 클래스가 아니고 `GetWindow` 는 04편 끝까지 쓰는 곳이 없어서, 이력을 다시 써 02편 2단계부터 뺐습니다

**규약 개편 (2026-09-26)**

근거는 같은 날의 코드 점검 둘입니다. 하나는 `tut04` 코드를 DirectXTK·MS 샘플·MS 문서와 대조했고, 하나는 경험자가 멈출 곳을 코드만 보고 찾았습니다.

- 머리에 원칙 두 줄을 넣었습니다. 복사 금지·전역 상수·`Initialize` 규칙이 클래스 성격을 가리지 않고 적용되어 복사되지 않는 값 타입, 멤버로 남은 시작 설정을 낳았습니다. 규칙이 없는 곳(의존 방향, 함수가 맡는 일, 짝 선언)에는 원문의 모양이 그대로 들어왔습니다
- 머리 둘째 원칙은 "기준 구현을 먼저 본다" 로 시작했다가 순서 목록으로 바꿨습니다(2026-09-27). 문장이 기준 구현으로 시작하고 1절이 맨 끝에 있으면, DirectXTK 의 일반화(옵션 플래그, 효과 인터페이스 계층)를 끌고 올 수 있습니다. 기준 구현이 없는 편에서 무엇을 따를지도 비어 있었습니다
- 설계 규칙에 대상과 이유를 붙였습니다. 대상은 이름이나 예·아니오 질문으로 적고, 새 예외는 규칙 문장을 고쳐서만 늘립니다
- 2절 `ComPtr` 주소 : `&` 를 쓰지 않습니다. `OMSetRenderTargets(1, &Rtv, ...)` 처럼 넘기면 호출 직전에 RTV 가 해제됩니다
- 3절 복사 금지를 핸들을 쥐거나 `this` 를 밖에 등록하는 클래스로 좁혔습니다. `FCamera` 같은 값 타입이 복사되지 않았고, `FModel`·`FColorShader` 는 이동까지 막혀 컨테이너에 담을 수 없었습니다
- 새 규칙 : 짝 선언(1절), 소유자가 가진 것(2절), 좁은 문자열 넓히기·고정 배열(5절), 셰이더 파일·그리기 함수 이름(6절), DirectXMath 인자·멤버와 include 방향(7절)
- 좁힌 규칙 : 추상화의 뜻(1절), raw 포인터(2절), `Initialize` 대상과 위임(3절), 시작 설정(7절 전역 상수), 선언 순서의 이유(7절)
- 지운 규칙 : 6절 "원문의 `Class` 접미사를 떼고 접두". 원문 클래스를 하나씩 옮기는 절차로 읽혀 원문의 클래스 경계를 끌고 왔습니다. 이름은 접두 표만으로 정해집니다
- DirectXMath 인자 : 04편은 `const XMMATRIX&` 로 시작했습니다. MS 관례를 따르기로 한 기준에 맞춰 바꿨습니다
- 기각 : 규칙마다 목적·대상·예외 칸을 두는 표. 모든 규칙이 세 줄 이상이 되고, 표기 규칙까지 칸을 채우면 소음이 됩니다
- 보류 : `new` 금지의 예외(private 생성자와 `std::unique_ptr<T>(new T())`). 싱글톤의 유일성을 컴파일러가 지키게 할 수 있지만, 싱글톤 기조와 함께 다룹니다
- 적용 : 코드는 배포 전에 한 번에 02~04편 이력에 반영합니다
**이력 분리 (2026-09-27)**

- `CODING_STYLE.md` 9절에 있던 날짜별 경위를 이 파일로 옮겼습니다. 9절이 96줄로 규칙 본문(171줄)의 절반을 넘어, 코드를 쓰는 세션이 매번 경위까지 읽었습니다. 경위 속 문장이 규칙처럼 읽힐 위험도 있었습니다
- 기각안은 본문 9절에 한 줄씩 모아 남겼습니다. 이력을 읽지 않은 세션이 기각한 안을 다시 올리지 않게 하려는 것입니다
- 기각 : 9절을 통째로 옮기는 안. 기각안까지 본문에서 빠집니다

# 교재 문서 규약

기준 시점 : 2026-09-27

dx-render-dojo 교재 문서의 편 구성과 문장 규칙입니다. 원고(`tools/doc-mock/template-NN.html`, NN 은 편 번호)를 쓰거나 고칠 때 읽습니다. 규칙을 바꿀 때는 이 문서를 고칩니다.

스테이지·편 제목·앞 편 태그는 목차 `tools/doc-mock/toc.json` 에 있습니다. 빌드가 원고 머리의 STAGE 줄과 이전 태그, 이전·다음 편 링크, 목차 페이지(`index.html`)를 여기서 채웁니다. 원고 `h1` 이 목차 제목과 다르면 빌드가 멈춥니다.

이 문서에서 "독자"는 DirectX 를 배우러 온 스터디원입니다. 리포를 관리하는 사람은 독자가 아닙니다. "원문"은 Rastertek DirectX 11 튜토리얼입니다. 독자는 원문을 보지 않습니다. 원문은 편마다 다룰 범위를 정할 때만 씁니다. 옛 한국어 정리 사이트(dxstudy-rastertek.vercel.app)는 참고하지 않습니다.

셀 수 있는 규칙은 `tools/doc-mock/check_prose.py` 가 봅니다. 나머지는 8절의 목록으로 사람이 읽어 봅니다.

## 1. 원칙

규칙끼리 부딪치면 번호가 작은 쪽을 따릅니다.

1. **사실이 맞음.** 따라 하기의 문장은 그 문장이 놓인 단계 커밋의 코드와 맞아야 하고, 한 단계의 주장이 다른 단계와 어긋나지 않아야 함. 뒤 단계에서야 참이 되는 주장은 그 단계로 옮기거나 "N단계부터" 를 붙임. 먼저 예측·다 됐는지 확인·흔한 실수·확인 문제·바꿔 보기는 편 태그 기준
2. **따라 치면 태그 코드가 됨.** 조각을 처음부터 순서대로 모두 옮기면 이 편의 태그 코드가 되어야 함. 독자는 편 끝에서 한 번 빌드·실행함. 조각의 조건은 2절
3. **독자에게 쓸모 있는 것만.** 리포 규약, 태그, 교재를 만든 사정, 작성자가 확인한 과정, 원문 언급·출처·원문과의 비교, VS 조작이 남기는 프로젝트 파일 diff 는 쓰지 않음. 이유를 적을 때는 독자에게 무엇이 달라지는지를 한 줄로. 예 : "왜 지금 만드나" 는 "2단계부터 쓰고 뒤 편에서도 계속 써요" 로 충분
4. **빼도 잃는 것이 없으면 뺌.** 5절의 사족 네 종류가 대표
5. **요점 먼저.** 단계는 말할 것 하나를 첫 문단에, 문단은 요점을 첫 문장에
6. **나머지 문장 규칙(4절).** 문장 규칙을 지키려고 1~5를 어기지 않음

8절의 수치는 결과를 보는 지표입니다. 수치를 맞추려고 문장을 고치지 않습니다.

## 2. 편 구성

- **편마다 핵심을 먼저 정함.** 다룰 범위는 원문의 그 편을 보고 정함. 학습 블록은 핵심에만 붙이고, 곁가지는 언급만 한 뒤 설명을 접음. 모든 것에 블록을 붙이면 무엇이 중요한지 흐려짐. 가르는 질문은 "뒤 편을 따라 하다가 이것을 모르면 막히나" 하나. 이 교재는 DX11 교재라 Win32 의 동작 원리는 모르고 지나가도 뒤 편에서 막히지 않음. 예 : 02편의 핵심은 뒤 편이 쓰는 셋(프레임마다 `Update`·`Render`, `CHECK_*` 와 로그, 창 크기 알림 `OnResize`)이고, 창 클래스·`this` 찾기·종료 경로·배율·전체 화면은 곁가지
- **곁가지 단계는 본문 한두 문단.** 학습 블록을 붙이지 않고 줄 단위 풀이와 개념 상자를 접음. 칠 코드는 곁가지여도 펼침. 예 : 02편 1단계는 `FLog`·`TSingleton`·`Check.cpp` 코드를 펼치고 풀이와 개념 상자를 접음
- **핵심 단계 안의 곁가지 설명도 접음.** 본문에는 그 코드가 하는 일을 한두 문장 두고, 이유와 동작 원리는 `자세히 · <주제>` 접기로 보냄. 접은 안쪽은 줄이지 않고 초보자가 읽을 수 있게 전제까지 풀어 씀. 예 : 02편 2단계 `Main.cpp` 는 본문에 "`Run` 이 `WM_QUIT` 을 꺼내야 돌아와요" 만 두고, 로그 콘솔을 먼저 여는 이유는 "Windows 는 키 입력을 맨 앞 창 하나에만 보낸다" 는 전제와 함께 접기에 둠
- **단계 순서는 독자가 따라가는 흐름.** 파일 의존 순서(타입 → 도구 → 선언 → 구현)로 늘어놓지 않음. 새 타입의 선언은 처음 쓰이는 단계에 둠. 예 : 02편은 메시지가 흐르는 순서로 7단계
- **단계 커밋은 조각을 뽑는 작성 도구.** 따라 하기의 단계 하나가 커밋 하나이고 N단계 커밋에 `tutNN-sN` 태그를 닮. 빌드가 이 커밋에서 조각을 꺼내므로 앞 단계 조각에 뒤 단계 줄이 섞이지 않음. 독자에게는 보이지 않음. 중간 커밋은 컴파일만 되면 됨(링크·실행 안 함). 컴파일이 "쓰기 전에 선언했는가" 를 확인함. 마지막 단계의 코드는 편 태그와 같고 빌드·실행됨
  - 단계 사이에서도 사람이 일하는 순서대로. 선언하는 단계가 쓰는 단계보다 먼저. 한 단계 안의 순서는 아래 코드 조각 줄
  - 함수는 되도록 한 단계에서 통째로 보임. 다른 단계의 주제인 줄만 그 단계로 미루고, 필요한 선언은 앞에서 먼저 침. 단계가 커지면 8절 지표로 봄
  - 중간 단계 코드는 최종 코드의 줄로만 씀. 임시 값을 쳤다가 뒤 단계에서 고치게 하지 않고, 뒤 단계의 이름은 부르지 않음. 중간 단계만을 위한 주석은 만들지 않음
  - 예외 : 뒤 단계가 함수를 통째로 바꾸고 그 이유가 교재 내용이면 앞 단계는 옛 모양으로 둠. 예 : 02편 2단계의 `FWindow::Initialize` 는 바깥 크기를 먼저 계산해 창을 만들고, 7단계가 배율을 읽으려고 창부터 만드는 모양으로 바꿈
  - 마커의 `@N` 이 N단계 커밋을 읽음. `DIFF@N` 은 N-1단계에서 N단계로 온 차이. `@` 가 없는 마커는 편 태그를 읽고 바뀐 파일 절에 씀
- **단계 하나는 주제 하나.** 새 파일이 여럿이고 조각이 길면(8절 지표) 나눌 수 있는지 봄. 나누면 중간 단계가 최종 코드의 줄로만 쓰이지 않을 때는 나누지 않고 `docs/DOC_STYLE_HISTORY.md` 에 이유를 남김. 예 : 04편은 셰이더 파일과 컴파일을 두 단계로 나눔. 02편 7단계(배율과 전체 화면)는 둘이 주석과 분기로 얽혀 나누지 않음
- **코드 조각은 따라 칠 수 있게.** 단계 순서는 흐름 그대로 두고 조각은 아래를 지킴
  - 빠짐없음 : N단계 diff 에서 바뀐 줄은 지운 줄까지 모두 N단계의 어느 조각에 나옴. 공백만 바뀐 줄과 끝의 바뀐 파일 절은 세지 않음
  - 보이는 방식 : 새 함수·클래스와 바뀐 함수는 통째로. 흩어진 한두 줄과 지운 줄은 범위 diff 로. 절반 넘게 바뀐 파일은 파일째
  - 새 파일 : 그 단계가 쓰는 include 와 멤버만 둠. 뒤 단계가 쓰는 것은 그 단계에서 diff 로 더함
  - 덩어리 순서 : 한 단계 안에서 한 덩어리(함수 본문, 클래스 선언, include 묶음)를 여러 조각으로 나눠 보이면 조각들이 빈틈없이 이어지고, 앞 조각이 소스에서도 앞
  - 배지 : 캡션에 할 일 하나. `신규` 는 새 파일·새 함수를 넣기, `수정` 은 있던 것을 고치기, `삭제` 는 통째로 지우기. diff 조각은 늘 `수정`. 머리말(section-note)도 이 뜻으로 씀
  - 넣을 자리 : 함수 중간 조각은 캡션이나 앞 문장에 자리를 적음. 예 : "`FD3D11Graphics::Initialize` 안, `CreateSwapChainForHwnd` 다음". 새 함수도 캡션에 자리를 적되, 그 단계까지 친 함수를 기준으로 적음. 예 : "`Initialize` 다음, `CreateSizeDependentResources` 앞". 범위 diff 는 바로 앞 문맥 줄에서 시작해 `+` 줄로 시작하지 않게 하고, 헝크가 둘 이상이면 자리를 모두 적음
  - 들여쓰기 : 조각은 소스의 들여쓰기 그대로
  - 한 단계 안에서는 선언을 쓰는 코드보다 먼저. 구조체·헤더를 cpp 보다 먼저 치고, 새 클래스를 만든 뒤 그 클래스를 부르는 쪽을 고침. 예 : 03편 3단계는 `FDisplaySettings::bVSync` → `FD3D11Graphics.h` → `Initialize` 순서
  - 프로젝트 파일 : 목적은 Visual Studio 로 따라 하는 독자가 문장만으로 같은 프로젝트를 만드는 것. 새 파일이 생기는 단계에서 등록함. 새 파일은 디스크 위치부터 안내함(따라 하기 머리말 : 캡션 경로는 리포 루트 기준, 새 항목 추가의 위치를 그 폴더로). 속성은 "구성 · 메뉴 경로 : 값" 을 한 줄에 하나씩 목록으로 적음. 적용해야 나타나는 페이지나 누르는 순서가 있으면 그 조건까지 적음. 인코딩이 중요한 파일은 저장 방법을 적음. `.vcxproj`·`.vcxproj.filters` 의 diff 는 보이지 않음. 독자는 VS 로 조작하고 파일을 읽지 않음
  - CMake : 01·02편 기본 세팅에서만 `CMake · 맥 빌드와 검사용, VS 만 쓰면 건너뜀` 접기로 다룸. 03편부터는 원고에 넣지 않음. 리포의 `CMakeLists.txt` 는 검사(clang-tidy)에 쓰므로 계속 맞춤
  - 옮긴 파일 : 어디서 어디로 옮기는지 문장으로 안내함. 파일 탐색기로 옮기고, 솔루션 탐색기에서 옛 항목을 제거한 뒤 기존 항목 추가로 다시 넣음. 조각은 바뀐 줄만 범위 diff 로 보임. 예 : 04편의 `Core` → `Utility`
- **새 이름은 코드나 개념 상자가 보여 준 뒤에 부름.** 앞에서 불러야 하면 "뒤에 나올 `FSystem`" 처럼 예고함. "한눈에 보기" 의 클래스 목록이 이 역할을 함
- **용어는 코드에 나온 것만으로 소개되지 않음.** D3D·Win32 용어는 처음 나오는 단계의 개념 상자나 본문에서 한 줄로 풂. 앞 편에서 풀었으면 다시 풀지 않음. 예 : 03편의 팩토리·정보 큐·디버그 레이어, 04편의 w = 1 과 -1~1 좌표
- **블록.** 먼저 예측 2문항, 자기 설명 질문(핵심 단계에만), 확인 문제 3문항(전부 핵심에서), 바꿔 보기(핵심을 건드리는 과제만), 다음 편 미리 생각하기 한 줄. 바뀐 파일은 접어 둠. 따라 하기 → 다 됐는지 확인 → 흔한 실수 순서
- **실행 결과는 편 끝 "다 됐는지 확인" 에 모음.** 단계 끝에 결과 상자를 두지 않음. 결과가 실행 조건에 따라 다르면 조건을 적음(6절). 예 : F5 로 실행하면 `CHECK_FATAL` 이 오류 상자보다 먼저 멈춤
- **먼저 예측 1번은 앞 편이 낸 질문을 받음.** 앞 편 "다음 편 미리 생각하기" 의 질문을 라벨 "NN편 끝에서 낸 질문" 으로 다시 내고 답을 둠

## 3. 단계와 문단

- **단계마다 말할 것 하나.** 그 요점에 걸리는 코드에만 본문을 쓰고, 나머지 코드의 설명은 그 코드 아래 줄 단위 풀이로 내림. 산문에 대한 규칙이고, 코드는 2절대로 빠짐없이 보임. "코드 → 한두 문장" 이 세 번 넘게 이어지면 설명서로 읽힘. 예 : 02편 2단계의 요점은 "800×600 은 클라이언트 영역 크기" 하나이고 `FDisplaySettings`·`FWindow` 선언 설명은 풀이가 맡음
- **문단은 요점으로 엶.** 첫 문장만 읽어도 그 문단이 무슨 말인지 알아야 함. 예 : "`Initialize` 가운데의 크기 계산은 800×600 이 클라이언트 영역의 크기라서 필요해요" 는 요점이 이유 절 안에 묻힘. "800×600 은 창 전체가 아니라 클라이언트 영역의 크기예요" 로 엶
- **단계 첫 문단도 요점이나 문제로 엶.** 앞 단계가 남긴 문제에서 출발하면 그 문제를 한 구절로 받아 이번 단계의 요점으로 엶. 회상 문장을 따로 두지는 않음. 모든 단계가 "앞 단계 회상 → 빈 곳 지적" 으로 열리면 그것이 틀로 보임. 예 : 02편 3단계는 "닫기를 제대로 처리하려면 창의 메시지를 `FWindow` 의 멤버 함수에서 받아야 해요" 로, 04편 7단계는 "삼각형이 창 비율을 따라 늘어나지 않게 하려면" 으로 엶
- **소제목(h3)은 2~5어절 동사구.** 같은 목적이 다음 편에 또 나오면 같은 라벨을 다시 씀. 목적이 같은 단계를 편끼리 알아보게 하는 장치(subgoal labeling)이고, 문체 리서치에서 프로그래밍 교육 실험 근거가 붙은 유일한 항목. 02편 라벨 : `공통 도구 셋을 미리 만들어 둔다` · `창을 만들고 메시지 루프를 돌린다` · `static 함수에서 객체를 찾는다` · `끝나는 길을 하나로 모은다` · `메시지를 맡을 곳으로 나눠 보낸다` · `창 크기를 알린다` · `배율과 전체 화면을 맞춘다`
- **문단을 요약 꼬리나 예고로 닫지 않음.** "N단계에서 봐요" 는 풀이 항목 끝이나 답 보기의 괄호 링크로 돌림. 코드에 이미 나온 이름에는 예고를 달지 않음
- **개수 선언으로 문단을 열지 않음.** "끝나는 길은 셋이에요" 대신 셋을 바로 나열함. 독자가 세어 확인할 값("새 `.cpp` 여섯 개")은 남김

## 4. 문장

- **어미.** 본문은 해요체. 불릿·레이블·표는 명사 종결, 제목은 동사구. 푸터의 라이선스 문구만 합쇼체
- **술어는 직설로.** 직설로 바꿔도 어색하지 않으면 바꿈(`깔아 둡니다` → `미리 만들어 둡니다`, `닿을 수 있게` → `부를 수 있게`). 이름으로 쓰는 비유(`곁가지`, `번호표`)와 프로그래밍 표준어(`넘기다`·`돌려주다`·`부르다`·`오다`)는 둠
- **코드 위치는 이름으로 가리킴.** "가운데", "맨 위", "아래 코드" 대신 함수·`case`·변수 이름을 씀. 같은 함수 안에 그 말이 다른 뜻으로 쓰일 자리가 있으면 잘못 읽힘. 예 : `FWindow::Initialize` 는 창을 화면 가운데에 놓는 계산도 해서 "가운데의 크기 계산" 이 그쪽으로 읽힘
- **두 문장은 인과나 대조일 때만 이음.** 상관없는 두 사실을 `-는데`·`-고` 로 잇지 않고 끊음. 예 : "`FInput` 은 … 기록하고, `FSystem` 은 창과 입력을 멤버로 가져요" 는 두 사실이라 나눔
- **쉼표는 주어가 바뀌는 긴 문장에.** 연결어미 뒤 쉼표는 기본으로 빼되, 주어가 바뀌어 한 번에 읽히지 않으면 남김. 예 : "창을 파괴하는 코드는 소멸자에만 두고, 끝내자는 신호는 `PostQuitMessage` 로만 보내요"
- **한 번에 한 뜻으로 읽힘.** 두 가지로 읽히는 문장은 풀어 씀. 부정이 어디까지 걸리는지("02편처럼 코어 하나를 다 쓰지 않아요" 는 02편도 안 쓴 것으로 읽힘), 기준 없는 방향("카메라를 10 뒤로" 는 z = -10 과 10 더 뒤 둘 다로 읽힘), 늘어나다와 커지다처럼 결과를 가르는 동사, 다른 동사와 활용형이 같은 말("끄는 동안" 은 끌다와 끄다), 두 겹 관형절, 한 문장에 두 걸음 넘는 계산이 대표
- **"~는 것은 ~예요" 정의문을 몰아 쓰지 않음.** 한 단계에 셋이 모이면 번역한 문장처럼 읽힘. 예 : v2 4단계의 "이 함수가 정하는 것은 …", "기준은 …", "등록하는 곳은 …"
- **지우지 않는 표현.** `~것이다`·`~를 통해`·문두 `또한`/`따라서` 는 사람이 더 많이 쓰는 표현이라 AI 티로 보고 지우지 않음
- **줄표(—) 대신 콜론이나 마침표**

## 5. 사족

빼도 독자가 잃는 정보가 없는 문장입니다. 02편은 v2 에서 v3 로 고치며 따라 하기 본문이 98문장에서 73문장으로 줄었고, 뺀 문장 대부분이 아래 넷이었습니다.

- **코드를 다시 읽어 주는 문장.** 바로 옆 코드나 코드 제목 줄이 보여 주는 것을 산문으로 옮긴 것. 예 : "`Update` 는 `FSystem::Get().GetInput()` 으로 입력을 읽고 ESC 가 눌려 있으면 `RequestExit` 을 불러요"
- **같은 설명의 반복.** 코드 주석, 개념 상자, 앞 단계, 예측 답이 이미 말한 것. 같은 어휘로 두 번 나오면 한 손이 쓴 티도 남음. 예 : "창마다 앱이 마음대로 쓰는 포인터 크기의 칸" 이 3단계 본문과 바로 아래 개념 상자에 둘 다 있었음
- **작성자가 확인한 과정.** 독자가 쓰는 것은 결과. 6절 참고. 예 : "컴퓨터를 실제로 꺼 가며 확인하기 어려워서 이 메시지를 창에 직접 보내 봤어요"
- **지금 몰라도 되는 예고.** 뒤 편의 계획이나 아직 쓰이지 않는 코드의 현재 상태. 예 : "시간을 다루는 편에서는 `Update` 가 경과 시간을 받게 돼요", "`OnResize` 는 아직 로그만 남겨요"

허용하는 반복은 하나입니다. 같은 사실을 본문과 흔한 실수에 둘 다 둘 수 있습니다. 본문은 "왜", 흔한 실수는 증상과 해결을 맡고, 흔한 실수 항목 아래 `본문` 레이블 줄로 본문을 가리킵니다.

## 6. 실측과 숫자

- **독자가 자기 화면에서 볼 결과만 씀.** 확인한 방법과 순서는 쓰지 않고, 결과는 현재형으로 씀. 예 : "확인해 보니 `WM_GETMINMAXINFO` 가 먼저 왔고" → "`WM_GETMINMAXINFO` 가 먼저 와요"
- **방법은 빼도 결과를 바꾸는 조건은 남김.** 이 교재의 기준 조건은 Visual Studio · Debug · F5(디버거가 붙음) · 배율 100% 예요. 디버거 유무, 배율, 선택적 기능(그래픽 도구), 설치한 도구 집합(v143)에 따라 결과가 달라지면 그 조건을 붙이고, 조건마다 다르면 둘 다 적음. 작성자가 확인한 환경은 독자 환경이 아님. 예 : "F5 로 실행했다면 Visual Studio 가 `CHECK_FATAL` 줄에서 먼저 멈춰요"
- **결과를 확인한 방식보다 세게 쓰지 않음.** 디버거로 메시지를 보내 본 결과를 "끌어 옮겨 봤다" 로 쓰지 않음. 손으로 확인하지 않은 값은 원고에 넣기 전에 확인함
- **계산값은 계산값으로.** 측정하지 않은 값에 "였어요" 를 쓰지 않음. 환경 조건(배율 100%)을 붙이고, 조건이 다른 독자에게는 값이 달라질 수 있다고 알림. 예 : "배율 100% 에서는 … 바깥 크기가 816×639 가 돼요"
- **1인칭은 흔한 방식 대신 다른 길을 고른 자리에만.** "저는 다르게 정했어요" 처럼 판단을 밝힐 때 한 편에 한두 번. 막다른 길을 보여 주는 서술("`static` 을 지우고 빌드하면 … 에러가 나요")은 문제가 저절로 있는 자리에 한 번. 이 교재 코드가 그렇게 동작하는 이유는 본문에 둠. 예 : 03편 1단계의 "GPU 가 둘인 노트북은 기본 어댑터가 느린 쪽일 수 있어요"
- **실측 숫자는 과제로도 씀.** 본문이나 확인 목록에 한 번, 바꿔 보기에 한 번. 독자가 자기 화면에서 같은 숫자를 보면 과제의 출발점이 됨. 예 : 창을 옮기기만 해도 찍히는 `창 크기 변경 : 800x600` 이 02편 바꿔 보기 3번의 출발점
- **출처가 계획인 문장은 계획을 따라 고침.** 예 : 6단계의 "정리가 끝나기 전에 프로세스가 끝날 수 있어요" 는 볼트 계획 노트의 "고치지 않기로 한 것" 이 출처

## 7. 학습 블록과 접기

- **접기 라벨 다섯은 이름을 고정함.** `Win32 개념` · `D3D 개념` · `줄 단위 풀이` · `자세히` · `언리얼로 치면`. `D3D 개념` 은 Direct3D 와 DXGI 의 객체·용어를 담음. `자세히` 는 본문에서 뺀 이유와 동작 원리를 담고 `자세히 · <주제>` 로 씀. 내용이 있는 단계에만 둠. 모든 단계에 같은 접기가 붙으면 그것이 틀로 보임
- **`언리얼로 치면` 은 편마다 넣을지 정함.** 비교 대상이 그 편의 핵심일 때만 둠. 예 : 02편은 비교 대상이 모두 Win32 배관이라 뺌
- **접기는 읽을거리에만.** 칠 코드는 접지 않음. 접기 안의 코드는 읽을거리로 보여 건너뛰게 됨. 예외는 01·02편의 CMake 조각으로, VS 로 따라 하는 독자는 치지 않음
- **줄 단위 풀이는 그 코드 바로 아래.** 단계 끝으로 모으지 않음
- **개념 상자는 그 단계를 읽는 데 필요할 때만 펼쳐 둠.** 곁가지 단계의 개념 상자는 접음
- **자기 설명 질문이 묻는 것을 같은 단계 본문이 말하지 않음.** 겹치면 둘 중 하나를 뺌. 예 : 4단계 본문에서 키 입력이 거치는 함수 나열을 빼고 F1 추적 질문만 남김
- **흔한 실수의 증상은 이 교재 코드를 따라 한 독자가 실제로 볼 수 있는 것.** 증상이 나지 않는 항목은 본문으로 옮기거나 조건을 증상 줄에 적음. 원인과 증상은 한 가지 코드에서 함께 나는 것이어야 함. 예 : 04편 흔한 실수 1번은 원인을 "초기화 때 한 번 묶음" 으로, 증상을 "창 크기를 바꿀 때마다 경고" 로 적었는데, 초기화 때 한 번만 묶으면 경고는 시작할 때 두 줄뿐임
- **언리얼 상자는 엔진 소스로 확인한 심볼만.** 확인 목록은 볼트 `_ai/2026-09-20_튜토리얼-학습-방식-검토기록` 에 있음. 목록에 없으면 상자를 빼거나 엔진 소스에서 먼저 확인. 동작을 말하는 문장은 그 동작을 하는 소스 줄까지 확인함. 예 : 04편의 "먼 면이 없다" 는 `CalculateProjectionMatrix` 가 가까운 면만 넘기는 줄에서 확인
- **도식은 공간·구조·흐름이 있는 개념에 기본으로 넣음.** 말로만 붙잡기 어려운 관계를 그림 한 장이 보여 줌. 예 : 창 바깥 크기와 클라이언트 영역, `this` 를 창의 칸에 넣고 꺼내는 길, 스왑체인과 RTV, 입력 레이아웃, 파이프라인 지도, 카메라 옆모습
  - 코드가 이미 순서대로 보여 주는 것을 다시 그리지 않음. 꾸밈 그림은 넣지 않음
  - 인라인 SVG 로 그리고 색은 `dg-*` 클래스로 토큰을 따름. 다크 모드도 같은 클래스로 맞춰짐
  - 캡션은 한두 문장이고 그림이 말하는 요점을 적음. 본문은 그림을 다시 읽지 않음
  - 그림 속 숫자·이름·단계 번호는 그 단계 코드와 맞춤. 사실 대조(1절 1번) 대상임

## 8. 점검

`check_prose.py` 가 보는 것 : 마커와 태그 코드의 대응, 따라 하기 조각의 단계별 빠짐없음(`CMakeLists.txt` 는 01·02편만)과 덩어리 순서, 단계와 맞지 않는 `@N` 마커, 마지막 단계 커밋과 편 태그의 코드 일치, 프로젝트 파일이 바뀐 단계의 VS 조작 안내(솔루션 탐색기·항목 추가·필터·속성), 옮긴 파일의 언급과 바뀐 줄, 배지와 조각 종류의 짝, 추가 줄로 시작하는 범위 diff, 먼저 예측 1번의 라벨, 풀이가 가리키는 코드가 바로 위 조각에 있는지(생성 결과에서, 경고), 태그 짝과 앵커, 원문 언급(`원문`·`Rastertek`·`dxstudy`. 스크립트·스타일과 목차가 채우는 자리는 뺌), 단계 끝 `여기까지` 상자, 줄표, 본문 합쇼체, 금지 표현(메타 담화·강조 예고·술어 비유 등), 개수 선언으로 여는 문단, 예고 꼬리, 제목과 목록의 어미.

```
./tools/doc-mock/build.ps1 -Lesson 2
python tools/doc-mock/check_prose.py tools/doc-mock/template-02.html --tag tut02
python tools/doc-mock/check_prose.py tools/doc-mock/tutorial-02.html --built
```

`build.ps1` 을 인자 없이 돌리면 원고가 있는 편을 모두 다시 만듭니다. 새 편을 쓰면 앞 편의 다음 편 링크가 바뀌므로 인자 없이 돌립니다. 목차 페이지는 어느 쪽이든 다시 만듭니다.

검토는 세 단계로 합니다.

1. **작성 세션** : 원고를 쓰고 스크립트 점검을 통과시킴. 아래 "쓰면서 보는 것" 을 봄
2. **검토 세션** (작성 세션과 다른 세션)
   - 인수 시험 : 이전 태그를 빈 worktree 에 풀고, 원고 조각만 보고 처음부터 순서대로 모두 옮긴 뒤 편 끝에서 빌드·실행함. 편 태그와 diff 가 비는지 봄. 공백과 빈 줄은 무시하고, 프로젝트 파일은 빌드와 실행 결과로 판정. 단계 커밋은 차례로 컴파일만 해서 쓰기 전에 선언했는지 봄. 도구와 절차는 `tools/accept/README.md`
   - 읽기 검토 : 원고와 태그 코드만 보고 독자 역할로 막힘·잘못 읽힘·읽기 불편을 찾음. 스크립트와 작성자가 놓치는 빈자리(용어 풀이, 이유, 실행 조건, 단계 사이 연결)를 잡음. 나온 항목은 코드와 실행으로 사실을 확인한 뒤 반영
3. **조은님 따라 치기** : Visual Studio 에서 원고 문장만 보고 파일 만들기·필터·속성을 조작하고 F5 로 실행해 봄. 인수 시험은 조각을 기계로 옮겨서 VS 조작과 디버거 실행을 거치지 않음

쓰면서 보는 것 :

- 원고의 사실 주장을 태그의 코드와 대조. 특히 "항상", "몇 개든" 같은 전칭 주장
- 한 단계의 주장이 다른 단계의 코드·서술과 맞는지. 예 : v2 6단계의 "소멸자는 … 저절로 불리니 길이 몇 개든 따로 챙길 것이 없어요" 는 7단계가 `Release` 를 직접 부르고, 초기화 실패 경로는 그것도 거치지 않아 어긋났음
- 문단마다 요점이 첫 문장에 있는지
- 5절의 사족
- 스크립트가 "문단 끝의 짧은 문장" 으로 보고한 줄이 요약 꼬리인지
- 편 끝 "다 됐는지 확인" 의 결과는 실제로 빌드·실행해서 옮겨 적음
- 재구성 뒤 대조 : 단계 순서를 바꾸거나, 편 사이로 코드를 옮기거나, 단계를 나누면 옮겨진 문장을 하나씩 새 단계 코드와 맞춰 봄. 옮긴 문장은 앞 자리에서만 참이었을 수 있음. 이런 커밋 메시지에는 `점검 :` 줄로 무엇을 봤는지 적음
- 거슬러 찾기 : 설계 결정이 앞 편 내용을 뒤집으면 앞 편 원고, 앞 편 태그의 코드 주석, 이 문서의 예문을 함께 찾아 고침(`git grep`). 앞 편을 고치는 일은 소급 후보로 올림(리포 `CLAUDE.md` "지나간 편 고치기")
- 단계 크기 지표 : `check_prose.py` 가 찍는 단계별 추가 줄 수가 100줄을 넘으면 2절 기준으로 나눌 수 있는지 봄. 지표일 뿐 기준이 아님

원고를 고친 뒤에는 `python tools/doc-mock/compare.py tools/doc-mock/template-NN.html` 로 마지막 커밋과 나란히 비교해 봅니다. 뺀 문장과 새로 쓴 문장이 절별로 표시됩니다. `--rev` 로 다른 리비전, `--old` 로 다른 파일과도 비교합니다.

스크립트는 쉼표가 든 문장 비율과 100자 이상 문장 수를 사람·AI 참고치(쉼표 26%·61%, 1000문장당 91·8)와 함께 보고합니다. 방향만 봅니다. 비율을 낮추려고 쉼표를 빼다가 긴 문장이 한 번에 읽히지 않게 되면 되돌립니다.

## 9. 기각안

규칙을 바꾸자는 안이 여기 있으면 이유를 먼저 봅니다. 규칙이 언제, 왜 바뀌었는지는 `docs/DOC_STYLE_HISTORY.md` 에 있습니다.

- 단계마다 "왜 필요한가" 슬롯, h3 아래 "한 줄 what" 슬롯 : 모든 단계가 같은 칸으로 찍혀 나와 틀로 보임
- 간결판/상세판 토글 : 간결판에 손으로 적은 코드 조각이 생겼음
- 새 파일을 처음 나오는 단계에서 통째로 : 설명보다 칠 코드가 먼저 오고 뒤 단계 조각과 겹침
- 파일 순서(헤더 → cpp)로 단계 재배치 : 따라 치기에 필요한 것은 파일 순서가 아니라 빠짐없음·넣을 자리·덩어리 순서
- 조각은 최종 코드로 두고 "N단계에서 추가" 표시만 다는 안 : 앞 단계 조각이 뒤 단계 이름을 부름
- 단계 커밋 없이 조각 배치만 바꾸는 안 : 한 함수 가운데 섞인 뒤 단계 줄은 최종 코드에서 뺄 수 없음. 조각을 손으로 적으면 실제 코드와 어긋남
- 단계마다 빌드·실행과 단계 끝 결과 상자, 일부러 틀려 보는 확인 : 독자는 편 끝에서 빌드함. 단계마다 돌아가게 하려고 함수를 쪼개고 임시 값을 쳤다 고치게 했음
- `원문과 비교` 접기와 "원문과 다른 점" 표 : 독자는 원문을 보지 않음
- 카드 모양 목차 : 원고가 없는 편이 빈 카드로 늘어서 자리를 많이 차지했음

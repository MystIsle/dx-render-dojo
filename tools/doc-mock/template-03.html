DirectX 11 초기화

D3D11 을 초기화하고 창 안쪽을 회색으로 지워요. 화면에는 02편의 창에 색 하나가 칠해질 뿐이지만 04편부터 그리는 것은 이 편에서 만든 스왑체인을 거쳐 화면에 나가요.

먼저 예측

코드를 보기 전에 답을 하나씩 정해 두세요. 틀려도 돼요. 정해 둔 답이 있으면 코드를 읽다가 그 대목에서 멈추게 돼요.

1 · 02편 끝에서 낸 질문

그림을 그릴 버퍼를 만들 때 크기를 정해야 해요. FDisplaySettings 의 Width·Height 와 FWindow 의 GetWidth()·GetHeight() 중 어느 쪽을 써야 할까요?

답 보기

FWindow 쪽이에요. FDisplaySettings 의 800×600 은 배율 100% 에서의 크기라서 배율 175% 에서 시작하면 클라이언트 영역이 처음부터 1400×1050 이에요. 창 크기는 실행 중에도 바뀌고 FDisplaySettings 는 처음 값 그대로예요. (2단계)

2 · CPU 는 얼마나 쓸까요

02편 앱은 실행 중에 CPU 코어 하나를 다 썼어요. 이 편은 프레임마다 Present 를 불러 그린 것을 화면에 내보내요. CPU 사용량은 어떻게 될까요?

답 보기

코어 하나를 다 쓰지 않아요. vsync 를 켜 두면 프레임이 모니터 주사율보다 빨리 돌 수 없어서 루프가 Present 에서 쉬어요. (3단계)

따라 하기

코드 조각 위의 경로는 리포 루트 기준이에요. 새 파일은 그 폴더에 만들어요. Visual Studio 의 새 항목 추가는 기본 위치가 프로젝트 파일 옆이라 위치를 그 폴더로 바꿔야 해요. 배지는 할 일이에요. 신규는 새 파일이나 새 함수를 넣기, 수정은 있던 것을 고치기, 삭제는 지우기예요. 통째로 보이는 조각은 그대로 넣거나 바꿔 넣고, diff 조각은 초록 줄을 넣고 빨간 줄을 지워요. 단계마다 끝의 여기까지 상자대로 빌드하고 실행해 보세요.

  1. 어댑터를 고르고 디바이스를 만든다

    D3D11 로 GPU 를 쓰려면 디바이스와 디바이스 컨텍스트가 있어야 해요. 디바이스는 버퍼·텍스처·뷰 같은 자원을 만들고, 컨텍스트는 그 자원으로 GPU 에 명령을 보내요.

    D3D 개념 · 어댑터, 디바이스, 컨텍스트
    • DXGI : D3D 버전과 상관없이 그래픽 카드와 화면 출력을 다루는 층. 어댑터 나열과 스왑체인이 여기 속함
    • 어댑터(IDXGIAdapter1) : 그래픽 카드 하나. GPU 가 둘인 PC 는 어댑터도 둘
    • 디바이스(ID3D11Device) : 자원과 뷰를 만드는 객체. 여러 스레드에서 불러도 됨
    • 디바이스 컨텍스트(ID3D11DeviceContext) : 파이프라인 상태를 정하고 GPU 에 명령을 보내는 객체. 한 번에 한 스레드만 씀
    • 팩토리(IDXGIFactory2) : DXGI 의 시작점. 어댑터를 나열하고 스왑체인을 만듦
    • 기능 수준(D3D_FEATURE_LEVEL_11_0) : GPU 가 갖춰야 할 기능 묶음. 이 수준을 못 맞추는 GPU 에서는 디바이스 생성이 실패

    D3D 를 맡는 새 클래스 FD3D11Graphics 를 Source/Graphics 에 만들어요. 이 단계에서는 디바이스와 컨텍스트만 가져요.

    줄 단위 풀이
    • Microsoft::WRL::ComPtr COM 객체를 가리키는 스마트 포인터. 소멸할 때 Release 를 불러서 원문의 Shutdown 이 하던 해제를 대신함
    줄 단위 풀이
    • #include <dxgi1_6.h> 어댑터를 성능 순으로 고르는 IDXGIFactory6 가 이 헤더에 있음
    • using Microsoft::WRL::ComPtr; 이 파일 안에서는 ComPtr 로 줄여 씀

    GPU 가 둘인 노트북은 기본 어댑터가 느린 쪽일 수 있어요. FD3D11Graphics::Initialize 는 DXGI 팩토리로 가장 빠른 어댑터를 고르고 그 어댑터로 디바이스를 만들어요.

    D3D11CreateDevice 는 디바이스와 컨텍스트를 한 번에 돌려줘요.

    줄 단위 풀이
    • CreateDXGIFactory2(0, ...) 첫 인자는 팩토리를 만드는 플래그. 0 은 플래그 없음
    • EnumAdapterByGpuPreference IDXGIFactory6 에 있는 함수. DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE 는 성능이 높은 순서로 나열해서 0 번이 가장 빠른 GPU. IDXGIFactory6 가 없으면 첫 어댑터를 씀
    • DedicatedVideoMemory / 1024 / 1024 그래픽 카드 전용 메모리를 MB 로
    • D3D_DRIVER_TYPE_UNKNOWN 어댑터를 직접 넘길 때 드라이버 종류는 이 값이어야 함
    • &FeatureLevel, 1 요구하는 기능 수준 목록과 개수. 11_0 하나만 요구함
    • nullptr, (Device.GetAddressOf() 다음) 실제로 만들어진 기능 수준을 받는 칸. 하나만 요구해서 받지 않음
    • Device.GetAddressOf() 출력 인자도 GetAddressOf() 로 넘김. ComPtr 의 & 는 가리키던 객체를 먼저 해제함

    FD3D11Graphics 는 FSystem 의 멤버예요. FSystem::Initialize 가 창을 만든 다음 Graphics.Initialize 를 불러요.

    줄 단위 풀이
    • FD3D11Graphics Graphics; FWindow 뒤에 둬서 창보다 먼저 사라짐. 2단계의 스왑체인이 창에 그림을 내보냄

    새 파일을 빌드에 등록해요. Visual Studio 에서는 솔루션 탐색기에 Graphics 필터를 만들고 FD3D11Graphics.h·FD3D11Graphics.cpp 를 기존 항목 추가로 넣어요. 링크할 라이브러리는 프로젝트 속성에서 구성을 모든 구성으로 두고 링커 › 입력 › 추가 종속성에 d3d11.lib;dxgi.lib 를 더해요. 두 조작이 DxRenderDojo.vcxproj 와 DxRenderDojo.vcxproj.filters 를 바꿔요.

    참고 : 위 조작이 프로젝트 파일에 남기는 diff · 따로 치지 않음
    CMake · 맥 빌드와 검사용, VS 만 쓰면 건너뜀
    • target_link_libraries(DxRenderDojo PRIVATE d3d11 dxgi) 원문은 헤더의 #pragma comment(lib, ...) 로 링크함. mingw 빌드와 맞추려고 빌드 파일에 적음
    원문과 비교

    원문은 D3D11CreateDeviceAndSwapChain 한 번으로 디바이스·컨텍스트·스왑체인을 함께 만들고 어댑터 인자에 NULL 을 넘겨 기본 어댑터를 써요. EnumAdapters(0) 로 얻은 어댑터는 주사율과 카드 이름을 읽는 데만 써요. 원문 본문도 GPU 가 둘인 노트북에서는 기본 어댑터가 성능이 낮은 쪽일 수 있다고 적고 카드를 모두 나열해 사용자가 고르게 하라고 권해요.

    이 교재는 디바이스를 먼저 만들고 스왑체인은 2단계에서 따로 만들어요. 디바이스는 프로그램에 하나이고 스왑체인은 창에 딸린 것이에요.

    언리얼로 치면

    같은 점 · D3D11 백엔드인 FD3D11DynamicRHI 가 디바이스(Direct3DDevice)와 즉시 컨텍스트(Direct3DDeviceIMContext)를 하나씩 멤버로 가져요.

    다른 점 · 게임 코드는 FD3D11DynamicRHI 를 직접 쓰지 않고 그래픽 API 공통 층인 FDynamicRHI 를 거쳐요.

  2. 스왑체인을 만들고 백 버퍼를 연결한다

    화면에 보일 그림은 스왑체인이 가진 버퍼에 그려요. 앱이 백 버퍼에 그리는 동안 앞서 내보낸 버퍼가 화면에 쓰이고, Present 를 부르면 둘의 역할이 바뀌어요.

    D3D 개념 · 스왑체인과 뷰
    • 스왑체인(IDXGISwapChain1) : 창 하나에 딸린 버퍼 묶음. Present 때마다 그린 버퍼를 화면 쪽에 넘기고 다음 버퍼를 앱에 줌
    • 백 버퍼 : 앱이 지금 그리는 버퍼. GetBuffer(0) 이 돌려줌. Present 로 역할이 바뀌어도 이 버퍼로 만든 RTV 로 다음 프레임을 그림
    • 플립 모델(DXGI_SWAP_EFFECT_FLIP_DISCARD) : 버퍼를 복사하지 않고 화면 합성기(DWM)에 그대로 넘기는 방식. 버퍼가 2개 이상이어야 함
    • 뷰 : 자원을 파이프라인에서 어떻게 쓸지 정하는 객체. 텍스처는 렌더 타깃 뷰(RTV, ID3D11RenderTargetView)를 거쳐야 그림을 받는 대상이 됨

    스왑체인은 창에 딸려서 Initialize 가 이제 창을 받아요. 헤더에는 스왑체인과 RTV 멤버, RTV 를 만드는 함수를 더해요.

    줄 단위 풀이
    • class FWindow; 헤더에서는 참조로만 받아서 전방 선언으로 충분함
    • Window.GetWidth() 버퍼 크기는 창의 클라이언트 영역 크기. 먼저 예측 1번의 답
    • DXGI_FORMAT_R8G8B8A8_UNORM 한 픽셀에 R·G·B·A 각 8비트. UNORM 은 0~255 를 0.0~1.0 으로 읽는다는 뜻
    • SampleDesc.Count = 1 멀티샘플링을 쓰지 않음
    • DXGI_USAGE_RENDER_TARGET_OUTPUT 이 버퍼에 그린다는 선언
    • BufferCount = 2 플립 모델은 2개 이상이어야 함. 1 로 두면 흔한 실수 2번
    • CreateSwapChainForHwnd(Device.Get(), Window.GetHandle(), ...) D3D11 에서는 첫 인자로 디바이스를 넘김. 뒤의 두 nullptr 는 독점 전체 화면 설정과 출력 모니터 제한
    • CHECK_FATAL(Factory->CreateSwapChainForHwnd( 호출이 여러 줄에 걸치면 MSVC 빌드는 로그에 끝나는 줄 번호를 찍음. 디버거는 시작 줄에서 멈춤

    백 버퍼는 텍스처일 뿐이라 그대로는 지울 수도 그릴 수도 없어요. CreateSizeDependentResources 가 백 버퍼로 RTV 를 만들고, 3단계는 이 RTV 를 거쳐 백 버퍼를 지워요.

    원문과 비교

    원문은 백 버퍼 1개에 DXGI_SWAP_EFFECT_DISCARD 를 써요. 버퍼를 화면 쪽으로 복사하는 옛 방식이에요. 플립 모델에서는 버퍼 1개로 스왑체인을 만들 수 없어요.

    원문은 디스플레이 모드 목록에서 주사율을 찾아 스왑체인에 넣어요. 독점 전체 화면에서 쓰는 값이라 이 교재는 조회하지 않아요. DXGI_SWAP_CHAIN_DESC1 에는 주사율 칸도 없어요.

    언리얼로 치면

    같은 점 · 스왑체인은 창에 딸려요. D3D11 백엔드에서 창 하나를 맡는 FD3D11Viewport 가 창 핸들(WindowHandle)과 SwapChain 을 멤버로 가져요.

    다른 점 · 언리얼은 디바이스(FD3D11DynamicRHI)와 스왑체인(FD3D11Viewport)을 다른 클래스가 가져요. 이 교재는 창이 하나라 FD3D11Graphics 가 둘을 함께 가져요.

    스스로 설명해 보기

    CreateSizeDependentResources 의 BackBuffer 는 지역 변수라 함수가 끝나면 참조를 놓아요. 그런데도 RTV 로 백 버퍼를 계속 지울 수 있는 이유를 말해 보세요.

    여기까지

    실행하면 1단계와 같아 보여요. 스왑체인은 만들었지만 아직 아무것도 내보내지 않아요. 상자 없이 창이 뜨면 돼요.

  3. 매 프레임 지우고 내보낸다

    한 프레임은 백 버퍼를 지우는 것으로 시작해 Present 로 끝나요. 그 앞뒤를 FSystem::Frame 이 맡아서 FApplication::Render 는 그 사이에 그리기만 하면 돼요.

    설정부터 더해요. vsync 를 켤지는 FDisplaySettings 의 bVSync 가 정해요. 지우는 색은 장면이 정해서 FApplication 의 ClearColor 가 (0.5, 0.5, 0.5, 1) 이면 창 안쪽이 회색이 돼요.

    FD3D11Graphics 는 Initialize 에서 설정을 받아 bVSync 를 보관해요. 프레임 앞뒤에 부를 BeginScene·EndScene 도 더해요.

    Present 의 첫 인자는 화면이 몇 번 갱신될 때마다 한 프레임을 내보낼지예요. 1 을 넘기면 화면이 한 번 갱신될 때 한 프레임씩만 나가요. 내보내지 못한 프레임이 쌓여 있으면 Present 가 기다리고 루프도 그동안 멈춰요. 02편과 달리 코어 하나를 다 쓰지 않는 이유예요.

    줄 단위 풀이
    • ClearRenderTargetView(RenderTargetView.Get(), Color.data()) RTV 가 가리키는 백 버퍼 전체를 한 색으로 채움
    • bVSync ? 1 : 0 0 이면 기다리지 않고 바로 내보냄
    원문과 비교

    원문은 ApplicationClass::Render 가 BeginScene 과 EndScene 을 직접 불러요. 저는 이 둘을 FSystem::Frame 으로 옮겼어요. 그러면 편마다 Render 를 새로 써도 Present 를 빠뜨릴 일이 없어요.

    원문의 BeginScene 은 깊이 버퍼도 지워요. 이 편에는 깊이 버퍼가 없어요.

    언리얼로 치면

    같은 점 · 게임 코드는 Present 를 부르지 않아요. Slate 렌더러가 EndDrawingViewport 를 부르면 D3D11 백엔드의 FD3D11DynamicRHI::RHIEndDrawingViewport 를 거쳐 FD3D11Viewport 가 SwapChain->Present 를 불러요.

    다른 점 · 언리얼은 vsync 여부를 Present 까지 가는 호출마다 bLockToVsync 로 넘겨요. 이 교재는 초기화 때 읽은 bVSync 를 계속 써요.

    스스로 설명해 보기

    bVSync 를 끄면 Frame 이 1초에 몇 번 불릴지는 무엇이 정할까요? 모니터와 상관이 있을지도 말해 보세요.

    여기까지

    창 안쪽이 회색이 돼요. 작업 관리자에서 보면 02편과 달리 CPU 코어 하나를 다 쓰지 않아요.

  4. 창 크기를 따라 스왑체인을 바꾼다

    스왑체인 버퍼의 크기는 만들 때 정해지고 창을 따라 저절로 바뀌지 않아요. 3단계 코드로 창을 키워도 회색이 창을 채우는 것은 DXGI 가 처음 크기의 버퍼를 창에 맞게 늘려 보여 주기 때문이에요. 단색이라 티가 안 날 뿐 그림이 있으면 늘어나고 흐려져요. 창 크기가 바뀌면 ResizeBuffers 로 버퍼를 다시 만들어야 해요.

    ResizeBuffers 는 백 버퍼를 참조하는 RTV 가 남아 있으면 실패해요. 그래서 RTV 를 먼저 놓고 버퍼를 다시 만든 뒤 새 백 버퍼로 RTV 를 다시 만들어요.

    줄 단위 풀이
    • ResizeBuffers(0, ..., DXGI_FORMAT_UNKNOWN, 0) 첫 인자 0 과 DXGI_FORMAT_UNKNOWN 은 버퍼 개수와 형식을 그대로 둔다는 뜻
    • CreateSizeDependentResources(); 2단계에서 Initialize 가 부른 것과 같은 함수

    크기 알림은 02편의 FWindow::NotifyResize 에서 출발해요.

    NotifyResize 의 if (NewWidth == Width && NewHeight == Height) 가 02편 바꿔 보기 4번의 답이에요. 창을 옮기기만 하면 이제 로그도 찍히지 않고 스왑체인도 그대로예요.

    언리얼로 치면

    같은 점 · FD3D11Viewport::Resize 도 백 버퍼 참조를 먼저 놓고 ResizeBuffers 를 불러요. 소스 주석에 DXGI 가 요구하는 순서라고 적혀 있어요.

    다른 점 · 언리얼은 놓기 전에 백 버퍼와 그 뷰를 쓰는 곳이 하나뿐인지 checkComRefCount 로 검사해요. 이 교재는 검사 없이 ResizeBuffers 의 실패를 CHECK_FATAL 로 받아요.

    스스로 설명해 보기

    창을 최소화하면 클라이언트 영역이 0×0 이 돼요. 그래도 Resize 가 0×0 으로 불리지 않는 이유를 02편 HandleMessage 에서 찾아 말해 보세요.

    여기까지

    창을 옮기기만 하면 이제 창 크기 변경 이 찍히지 않아요. 테두리를 끌어 크기를 바꾸면 찍혀요. 버퍼를 다시 만드는지는 일부러 틀려 보고 확인해요. Resize 의 RenderTargetView.Reset(); 을 잠깐 주석으로 막고 최대화하면 [CHECK FATAL] SwapChain->ResizeBuffers(...) 와 HRESULT 0x887A0001 이 찍히고 상자가 떠요. 확인했으면 되돌려요.

  5. 디버그 메시지를 로그로 옮긴다

    D3D 와 DXGI 에는 디버그 레이어가 있어요. 켜 두면 잘못된 호출의 원인을 영어 문장으로 알려 줘요. 이 단계는 디버그 빌드에서 그 레이어를 켜고 문장을 FLog 로 옮겨요. 그러면 콘솔 창에서 [CHECK FATAL] 줄 바로 위에 원인이 찍혀요. 흔한 실수 두 항목의 증상이 그 예예요.

    디버그 레이어는 Windows 선택적 기능 "그래픽 도구" 에 들어 있어요. 없으면 시작할 때 [경고] D3D 디버그 레이어가 없어 끄고 진행한다 가 찍혀요. 설정의 선택적 기능에서 그래픽 도구를 추가하면 켜져요.

    치명 실패로 끝나기 직전에도 쌓인 메시지를 내보내야 원인이 보여요. 그래서 ReportFatal 이 로그와 상자보다 먼저 부를 훅을 Check 에 더해요.

    줄 단위 풀이
    • const std::function<void()> Hook = std::move(FatalHook); 훅을 꺼내 비운 뒤 부름. 훅 안에서 다시 치명 실패가 나도 훅이 두 번 불리지 않음

    디버그 레이어는 메시지를 정보 큐(IDXGIInfoQueue)에 쌓아 두고, 앱은 거기서 꺼내 읽어요. FD3D11Graphics 는 그 큐와, 메시지를 꺼내 로그로 옮기는 FlushDebugMessages 를 가져요. 소멸자는 Initialize 에서 걸 훅을 풀어요.

    줄 단위 풀이
    • #include <initguid.h> 다른 헤더보다 먼저 와야 그 뒤 헤더가 선언하는 GUID 가 이 파일에서 정의됨
    줄 단위 풀이
    • ::Return::SetFatalHook(nullptr); 훅은 이 객체의 주소(this)를 붙잡고 있음. 복사를 막아 둬서 객체가 옮겨지지 않으니 소멸할 때 한 번만 풀면 됨

    디버그 코드는 모두 #ifndef NDEBUG 안이라 릴리스 빌드에는 들어가지 않아요. Visual Studio 출력 창에는 DXGI 메시지가 두 번 찍혀요. 한 번은 DXGI 런타임이, 한 번은 FLog 가 찍어요.

    줄 단위 풀이
    • D3D_DRIVER_TYPE_NULL 화면에 그리지 않는 드라이버. 디버그 레이어가 있는지만 보려고 이 드라이버로 디바이스를 먼저 만들어 봄

    메시지는 DXGI 정보 큐 하나에서 꺼내요. 스왑체인 메시지는 DXGI 쪽이라 D3D11 의 ID3D11InfoQueue 로는 받지 못해요. 꺼내는 때는 Initialize 끝, Present 뒤마다, 그리고 치명 실패로 끝나기 직전이에요.

    줄 단위 풀이
    • GetMessage(DXGI_DEBUG_ALL, Index, nullptr, &Length) 처음에는 길이만 받고, 그만큼 버퍼를 잡은 뒤 다시 불러 내용을 받음
    • CHECK_RETURN(...) 메시지 하나를 못 꺼내는 것은 치명 실패로 볼 일이 없어 함수만 빠져나옴
    • Message->Producer == DXGI_DEBUG_DXGI 메시지를 낸 쪽에 따라 [DXGI]·[D3D] 를 붙임

    여기까지

    겉모습은 4단계와 같아요. 2단계의 BufferCount 를 1 로 바꾸고 Ctrl+F5 로 실행하면 상자가 뜨기 전에 콘솔에 [DXGI] 로 시작하는 원인 문장이 찍혀요. F5 로 실행했다면 Visual Studio 가 CHECK_FATAL 줄에서 먼저 멈춰요. 계속(F5)을 누르면 문장이 찍히고 상자가 떠요. 그래픽 도구가 없으면 이 문장 대신 시작할 때 경고만 찍혀요. 확인했으면 2 로 되돌리고 다 됐는지 확인 목록과 맞춰 보세요.

흔한 실수

창 크기를 바꾸는 순간 상자가 뜨고 종료 코드 1. 디버그 빌드 콘솔에는 [에러] [DXGI] IDXGISwapChain::ResizeBuffers: Swapchain cannot be resized unless all outstanding buffer references have been released. 다음 [CHECK FATAL] SwapChain->ResizeBuffers(...) 와 HRESULT 0x887A0001

원인Resize 에서 ResizeBuffers 전에 RTV 를 놓지 않았어요. RTV 가 아직 백 버퍼를 참조하고 있어서 ResizeBuffers 가 DXGI_ERROR_INVALID_CALL(0x887A0001)로 실패해요.

해결RenderTargetView.Reset() 과 Context->Flush() 를 ResizeBuffers 앞에 두고 뒤에서 RTV 를 다시 만들어요.

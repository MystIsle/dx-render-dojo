DirectX 11 초기화

D3D11 을 초기화하고 창 안쪽을 회색으로 지워요. 화면에는 02편의 창에 색 하나가 칠해질 뿐이지만 04편부터 그리는 것은 이 편에서 만든 스왑체인을 거쳐 화면에 나가요.

이 편을 마치면

  • 실행안쪽이 회색인 창이 뜨고 로그에 그래픽 카드 이름과 전용 메모리가 찍힘
  • 디바이스어댑터를 골라 디바이스와 컨텍스트를 만들고, 스왑체인의 백 버퍼에 RTV 를 연결하는 순서
  • 프레임매 프레임 백 버퍼를 지우고 Present 로 내보내는 틀. vsync 가 켜져 있으면 CPU 코어 하나를 다 쓰지 않음
  • 크기창 크기·배율·전체 화면이 바뀔 때 스왑체인 버퍼를 창에 맞춰 다시 만드는 길

먼저 예측

코드를 보기 전에 답을 하나씩 정해 두세요. 틀려도 돼요. 정해 둔 답이 있으면 코드를 읽다가 그 대목에서 멈추게 돼요.

1 · 02편 끝에서 낸 질문

그림을 그릴 버퍼를 만들 때 크기를 정해야 해요. FDisplaySettings 의 Width·Height 와 FWindow 의 GetWidth()·GetHeight() 중 어느 쪽을 써야 할까요?

답 보기

FWindow 쪽이에요. FDisplaySettings 의 800×600 은 배율 100% 에서의 크기라서 배율 175% 에서 시작하면 클라이언트 영역이 처음부터 1400×1050 이에요. 창 크기는 실행 중에도 바뀌고 FDisplaySettings 는 처음 값 그대로예요. (2단계)

2 · CPU 는 얼마나 쓸까요

02편 앱은 실행 중에 CPU 코어 하나를 다 썼어요. 이 편은 프레임마다 Present 를 불러 그린 것을 화면에 내보내요. CPU 사용량은 어떻게 될까요?

답 보기

코어 하나를 다 쓰지 않아요. vsync 를 켜 두면 프레임이 모니터 주사율보다 빨리 돌 수 없어서 루프가 Present 에서 쉬어요. (3단계)

따라 하기

코드 조각 위의 경로는 리포 루트 기준이에요. 새 파일은 그 폴더에 만들어요. Visual Studio 의 새 항목 추가는 기본 위치가 프로젝트 파일 옆이라 위치를 그 폴더로 바꿔야 해요. 배지는 할 일이에요. 신규는 새 파일이나 새 함수를 넣기, 수정은 있던 것을 고치기, 삭제는 지우기예요. 통째로 보이는 조각은 그대로 넣거나 바꿔 넣고, diff 조각은 초록 줄을 넣고 빨간 줄을 지워요. 빌드와 실행은 6단계까지 친 뒤 다 됐는지 확인에서 한 번 해요.

  1. 어댑터를 고르고 디바이스를 만든다

    D3D11 로 GPU 를 쓰려면 디바이스와 디바이스 컨텍스트가 있어야 해요. 디바이스는 버퍼·텍스처·뷰 같은 자원을 만들고, 컨텍스트는 그 자원으로 GPU 에 명령을 보내요.

    D3D 개념 · 어댑터, 디바이스, 컨텍스트
    • DXGI : D3D 버전과 상관없이 그래픽 카드와 화면 출력을 다루는 층. 어댑터 나열과 스왑체인이 여기 속함
    • 어댑터(IDXGIAdapter1) : 그래픽 카드 하나. GPU 가 둘인 PC 는 어댑터도 둘
    • 디바이스(ID3D11Device) : 자원과 뷰를 만드는 객체. 여러 스레드에서 불러도 됨
    • 디바이스 컨텍스트(ID3D11DeviceContext) : 파이프라인 상태를 정하고 GPU 에 명령을 보내는 객체. 한 번에 한 스레드만 씀
    • 팩토리(IDXGIFactory2) : DXGI 의 시작점. 어댑터를 나열하고 스왑체인을 만듦
    • 기능 수준(D3D_FEATURE_LEVEL_11_0) : GPU 가 갖춰야 할 기능 묶음. 이 수준을 못 맞추는 GPU 에서는 디바이스 생성이 실패

    D3D 를 맡는 새 클래스 FD3D11Graphics 를 Source/Graphics 에 만들어요. 이 단계에서는 디바이스와 컨텍스트만 가져요.

    Initialize 는 창 객체 대신 창 핸들과 크기, vsync 여부를 받아요. FWindow 는 Core 에 있는 클래스라, 받으면 Graphics 가 Core 를 알아야 해요. 기본 값만 받으면 FD3D11Graphics 를 떼어 다른 창에도 붙일 수 있어요. 창 핸들과 크기는 2단계의 스왑체인이, vsync 여부는 3단계의 Present 가 써요.

    줄 단위 풀이
    • Microsoft::WRL::ComPtr COM 객체를 가리키는 스마트 포인터. 소멸할 때 Release 를 불러서 따로 해제할 필요가 없음
    • FD3D11Graphics(const FD3D11Graphics& Other) = delete; 복사 금지. 6단계에서 이 객체의 주소(this)를 치명 실패 훅에 맡기므로 객체가 복사되거나 옮겨지면 안 됨
    • HWND WindowHandle HWND 는 d3d11.h 가 이미 끌어오는 Windows.h 의 형이라 따로 include 하지 않음
    줄 단위 풀이
    • #include <dxgi1_6.h> 어댑터를 외장 GPU 부터 나열하는 IDXGIFactory6 가 이 헤더에 있음
    • using Microsoft::WRL::ComPtr; 이 파일 안에서는 ComPtr 로 줄여 씀

    GPU 가 둘인 노트북은 기본 어댑터가 느린 쪽일 수 있어요. FD3D11Graphics::Initialize 는 DXGI 팩토리로 외장 그래픽 카드를 먼저 고르고 그 어댑터로 디바이스를 만들어요.

    D3D 개념 · COM 인터페이스와 번호 붙은 버전
    • 인터페이스 : D3D·DXGI 객체는 COM 객체이고, 객체 하나가 인터페이스 여럿을 가질 수 있음. 아래 코드의 팩토리 객체 하나가 IDXGIFactory2 로도, IDXGIFactory6 로도 보임
    • 번호 붙은 인터페이스 : COM 은 한 번 내놓은 인터페이스를 고치지 않고, 기능을 더할 때 번호를 붙인 새 인터페이스를 만듦. exe 는 함수를 인터페이스 안의 칸 번호로 부르도록 컴파일되고 d3d11.dll·dxgi.dll 은 Windows 와 함께 따로 바뀜. 옛 인터페이스를 고치면 옛 exe 가 엉뚱한 함수를 부르게 됨. 그래서 기본 버전으로 만들고 새 기능만 따로 물음
    • QueryInterface · As : 같은 객체에 다른 인터페이스가 있는지 묻고, 있으면 그 포인터를 줌. 없으면 E_NOINTERFACE 로 실패. ComPtr 를 들고 있으면 As(&Other) 로 물음. 언리얼에서 Cast 로 인터페이스를 묻는 것과 같은 자리
    • IID_PPV_ARGS(포인터) : COM 함수가 받는 두 인자, 원하는 인터페이스의 ID 와 결과를 받을 void** 를 포인터의 형에서 한 번에 만드는 매크로. 둘을 손으로 쓰면 ID 와 포인터 형이 어긋나도 컴파일이 됨

    D3D11CreateDevice 는 디바이스와 컨텍스트를 한 번에 돌려줘요.

    줄 단위 풀이
    • UINT FactoryFlags = 0; 팩토리를 만드는 플래그. 디버그 빌드에서 5단계가 이 변수에 플래그를 더함
    • Factory.As(&Factory6) 같은 팩토리에 IDXGIFactory6 가 있는지 물음. 오래된 Windows 에는 없어서 실패하면 else 로 감. 실패해도 대신할 길이 있어 CHECK_* 가 아닌 if 로 받음
    • EnumAdapterByGpuPreference IDXGIFactory6 에 있는 함수. DXGI_GPU_PREFERENCE_HIGH_PERFORMANCE 는 외부 GPU(썬더볼트 박스 등), 외장 그래픽 카드, 내장 그래픽 순으로 나열함. 같은 종류끼리의 순서는 문서에 없어서 외장 카드가 둘이면 0 번이 더 빠른 쪽이라는 보장은 없음. IDXGIFactory6 가 없으면 첫 어댑터를 씀
    • DedicatedVideoMemory / 1024 / 1024 그래픽 카드 전용 메모리를 MB 로
    • UINT Flags = 0; 디바이스를 만드는 플래그. 디버그 빌드에서 5단계가 디버그 레이어 플래그를 더함
    • D3D_DRIVER_TYPE_UNKNOWN 어댑터를 직접 넘길 때 드라이버 종류는 이 값이어야 함
    • &FeatureLevel, 1 요구하는 기능 수준 목록과 개수. 11_0 하나만 요구함
    • nullptr, (Device.ReleaseAndGetAddressOf() 다음) 실제로 만들어진 기능 수준을 받는 칸. 하나만 요구해서 받지 않음
    • Device.ReleaseAndGetAddressOf() 결과를 받아 오는 출력 인자. 들고 있던 객체가 있으면 먼저 놓고 빈 칸의 주소를 넘겨서, 다시 받아도 옛 객체가 새지 않음. ComPtr 의 & 도 같은 일을 하지만 이름에 드러나지 않아 쓰지 않음

    FD3D11Graphics 는 FSystem 의 멤버예요. FSystem::Initialize 가 창을 만든 다음 Graphics.Initialize 를 불러요. vsync 여부는 시작 설정 FDisplaySettings 에 더해요.

    줄 단위 풀이
    • FD3D11Graphics Graphics; FWindow 뒤에 둬서 창보다 먼저 사라짐. 2단계의 스왑체인이 창에 그림을 내보냄

    새 파일을 빌드에 등록해요. Visual Studio 에서는 솔루션 탐색기에 Graphics 필터를 만들고 FD3D11Graphics.h·FD3D11Graphics.cpp 를 기존 항목 추가로 넣어요. 링크할 라이브러리는 프로젝트 속성에서 구성을 모든 구성으로 두고 링커 › 입력 › 추가 종속성의 맨 앞에 d3d11.lib;dxgi.lib; 를 더해요.

    언리얼로 치면

    같은 점 · D3D11 백엔드인 FD3D11DynamicRHI 가 디바이스(Direct3DDevice)와 즉시 컨텍스트(Direct3DDeviceIMContext)를 하나씩 멤버로 가져요.

    다른 점 · 게임 코드는 FD3D11DynamicRHI 를 직접 쓰지 않고 그래픽 API 공통 층인 FDynamicRHI 를 거쳐요.

    스스로 설명해 보기

    3단계에서 백 버퍼를 지우는 함수 ClearRenderTargetView 는 Device 와 Context 중 어느 쪽에 있을까요? 이 단계의 설명으로 이유까지 말해 보세요.

  2. 스왑체인을 만들고 백 버퍼를 연결한다

    화면에 보일 그림은 스왑체인이 가진 버퍼에 그려요. 앱이 백 버퍼에 그리는 동안 앞서 내보낸 버퍼가 화면에 쓰이고, Present 를 부르면 둘의 역할이 바뀌어요.

    D3D 개념 · 스왑체인과 뷰
    • 스왑체인(IDXGISwapChain1) : 창 하나에 딸린 버퍼 묶음. Present 때마다 그린 버퍼를 화면 쪽에 넘기고 다음 버퍼를 앱에 줌
    • 백 버퍼 : 앱이 지금 그리는 버퍼. GetBuffer(0) 이 돌려줌. Present 로 역할이 바뀌어도 이 버퍼로 만든 RTV 로 다음 프레임을 그림
    • 플립 모델(DXGI_SWAP_EFFECT_FLIP_DISCARD) : 버퍼를 복사하지 않고 화면 합성기(DWM)에 그대로 넘기는 방식. 버퍼가 2개 이상이어야 함
    • 뷰 : 자원을 파이프라인에서 어떻게 쓸지 정하는 객체. 텍스처는 렌더 타깃 뷰(RTV, ID3D11RenderTargetView)를 거쳐야 그림을 받는 대상이 됨

    헤더에는 스왑체인과 RTV 멤버, RTV 를 만드는 함수를 더해요.

    스왑체인은 1단계에서 받아 둔 창 핸들과 크기로 만들어요. Initialize 끝, 디바이스를 만든 다음에 이어 붙여요.

    줄 단위 풀이
    • SwapChainDesc.Width = static_cast<UINT>(Width); 버퍼 크기는 창의 클라이언트 영역 크기. FSystem 이 Window.GetWidth() 를 넘김. 먼저 예측 1번의 답
    • DXGI_FORMAT_R8G8B8A8_UNORM 한 픽셀에 R·G·B·A 각 8비트. UNORM 은 0~255 를 0.0~1.0 으로 읽는다는 뜻
    • SampleDesc.Count = 1 멀티샘플링을 쓰지 않음
    • DXGI_USAGE_RENDER_TARGET_OUTPUT 이 버퍼에 그린다는 선언
    • BufferCount = 2 플립 모델은 2개 이상이어야 함. 1 로 두면 흔한 실수 2번
    • CreateSwapChainForHwnd(Device.Get(), WindowHandle, ...) D3D11 에서는 첫 인자로 디바이스를 넘김. 뒤의 두 nullptr 는 독점 전체 화면 설정과 출력 모니터 제한
    • CHECK_FATAL(Factory->CreateSwapChainForHwnd( 호출이 여러 줄에 걸치면 MSVC 빌드는 로그에 끝나는 줄 번호를 찍음. 디버거는 시작 줄에서 멈춤
    • MakeWindowAssociation(WindowHandle, DXGI_MWA_NO_ALT_ENTER) 02편의 Alt+Enter 는 테두리 없는 창을 모니터 크기로 키울 뿐이라, DXGI 가 따로 거는 독점 전체 화면 전환은 끔

    백 버퍼는 텍스처일 뿐이라 그대로는 지울 수도 그릴 수도 없어요. CreateSizeDependentResources 가 백 버퍼로 RTV 를 만들고, 3단계는 이 RTV 를 거쳐 백 버퍼를 지워요.

    언리얼로 치면

    같은 점 · 스왑체인은 창에 딸려요. D3D11 백엔드에서 창 하나를 맡는 FD3D11Viewport 가 창 핸들(WindowHandle)과 SwapChain 을 멤버로 가져요.

    다른 점 · 언리얼은 디바이스(FD3D11DynamicRHI)와 스왑체인(FD3D11Viewport)을 다른 클래스가 가져요. 이 교재는 창이 하나라 FD3D11Graphics 가 둘을 함께 가져요.

    스스로 설명해 보기

    CreateSizeDependentResources 의 BackBuffer 는 지역 변수라 함수가 끝나면 참조를 놓아요. 그런데도 RTV 로 백 버퍼를 계속 지울 수 있는 이유를 말해 보세요.

  3. 매 프레임 지우고 내보낸다

    한 프레임은 백 버퍼를 지우는 것으로 시작해 Present 로 끝나요. 그 앞뒤를 FSystem::Frame 이 맡아서 FApplication::Render 는 그 사이에 그리기만 하면 돼요.

    지우는 색과 vsync 여부는 FD3D11Graphics 가 들고 있어요. 백 버퍼를 지우는 BeginScene 과 내보내는 EndScene 이 이 클래스에 있기 때문이에요. 지우는 색의 기본값은 회색 (0.5, 0.5, 0.5, 1) 이에요.

    줄 단위 풀이
    • DXGI_RGBA ClearColor Windows SDK 가 주는 색 구조체. float r, g, b, a 넷이 이 순서로 이어져 있음. 0.0~1.0 으로 적음

    Initialize 는 1단계에서 받은 bEnableVSync 를 멤버에 옮겨 둬요.

    Present 의 첫 인자는 화면이 몇 번 갱신될 때마다 한 프레임을 내보낼지예요. 1 을 넘기면 화면이 한 번 갱신될 때 한 프레임씩만 나가요. 내보내지 못한 프레임이 쌓여 있으면 Present 가 기다리고 루프도 그동안 멈춰요. 02편과 달리 코어 하나를 다 쓰지 않는 이유예요.

    줄 단위 풀이
    • ClearRenderTargetView(RenderTargetView.Get(), &ClearColor.r) RTV 가 가리키는 백 버퍼 전체를 한 색으로 채움. 둘째 인자는 float 4개 배열이라 이어져 있는 첫 멤버의 주소를 넘김
    • bVSync ? 1 : 0 0 이면 기다리지 않고 바로 내보냄

    BeginScene·EndScene 을 장면이 아니라 FSystem::Frame 이 불러요. 그러면 편마다 Render 를 새로 써도 Present 를 빠뜨릴 일이 없어요. 이 편의 장면은 그릴 것이 없어서 FApplication 은 바뀌지 않아요.

    언리얼로 치면

    같은 점 · 게임 코드는 Present 를 부르지 않아요. Slate 렌더러가 EndDrawingViewport 를 부르면 D3D11 백엔드의 FD3D11DynamicRHI::RHIEndDrawingViewport 를 거쳐 FD3D11Viewport 가 SwapChain->Present 를 불러요.

    다른 점 · 언리얼은 vsync 여부를 Present 까지 가는 호출마다 bLockToVsync 로 넘겨요. 이 교재는 초기화 때 받은 bVSync 를 계속 써요.

    스스로 설명해 보기

    bVSync 를 끄면 Frame 이 1초에 몇 번 불릴지는 무엇이 정할까요? 모니터와 상관이 있을지도 말해 보세요.

  4. 창 크기를 따라 스왑체인을 바꾼다

    스왑체인 버퍼의 크기는 만들 때 정해지고 창을 따라 저절로 바뀌지 않아요. 버퍼를 그대로 두고 창을 키우면 DXGI 가 처음 크기의 버퍼를 창에 맞게 늘려 보여 줘요. 단색이면 티가 안 나지만 그림이 있으면 늘어나고 흐려져요. 창 크기가 바뀌면 ResizeBuffers 로 버퍼를 다시 만들어야 해요.

    ResizeBuffers 는 백 버퍼를 참조하는 RTV 가 남아 있으면 실패해요. 그래서 RTV 를 먼저 놓고 버퍼를 다시 만든 뒤 새 백 버퍼로 RTV 를 다시 만들어요.

    줄 단위 풀이
    • ResizeBuffers(0, ..., DXGI_FORMAT_UNKNOWN, 0) 첫 인자 0 과 DXGI_FORMAT_UNKNOWN 은 버퍼 개수와 형식을 그대로 둔다는 뜻
    • CreateSizeDependentResources(); 2단계에서 Initialize 가 부른 것과 같은 함수

    크기 알림은 02편의 FWindow::NotifyResize 에서 출발해요.

    NotifyResize 의 if (NewWidth == Width && NewHeight == Height) 가 02편 바꿔 보기 3번의 답이에요. 창을 옮기기만 하면 이제 로그도 찍히지 않고 스왑체인도 그대로예요.

    언리얼로 치면

    같은 점 · FD3D11Viewport::Resize 도 백 버퍼 참조를 먼저 놓고 ResizeBuffers 를 불러요. 소스 주석에 DXGI 가 요구하는 순서라고 적혀 있어요.

    다른 점 · 언리얼은 놓기 전에 백 버퍼와 그 뷰를 쓰는 곳이 하나뿐인지 checkComRefCount 로 검사해요. 이 교재는 검사 없이 ResizeBuffers 의 실패를 CHECK_FATAL 로 받아요.

    스스로 설명해 보기

    창을 최소화하면 클라이언트 영역이 0×0 이 돼요. 그래도 Resize 가 0×0 으로 불리지 않는 이유를 02편 HandleMessage 에서 찾아 말해 보세요.

  5. 디버그 메시지를 로그로 옮긴다

    D3D 와 DXGI 에는 디버그 레이어가 있어요. 켜 두면 잘못된 호출의 원인을 영어 문장으로 알려 줘요. 이 단계는 디버그 빌드에서 그 레이어를 켜고 문장을 FLog 로 옮겨요. 디버그 코드는 모두 #ifndef NDEBUG 안이라 릴리스 빌드에는 들어가지 않아요.

    디버그 레이어는 Windows 선택적 기능 "그래픽 도구" 에 들어 있어요. 없으면 시작할 때 [경고] D3D 디버그 레이어가 없어 끄고 진행한다 가 찍혀요. 설정의 선택적 기능에서 그래픽 도구를 추가하면 켜져요.

    디버그 레이어는 메시지를 정보 큐(IDXGIInfoQueue)에 쌓아 두고, 앱은 거기서 꺼내 읽어요. FD3D11Graphics 는 그 큐와, 메시지를 꺼내 로그로 옮기는 FlushDebugMessages 를 가져요.

    1단계에서 0 으로 둔 두 플래그 변수 뒤에 디버그 블록을 하나씩 끼워 넣어요. 팩토리는 디버그 팩토리로, 디바이스는 디버그 레이어를 켜서 만들어요.

    줄 단위 풀이
    • DXGIGetDebugInterface1(0, IID_PPV_ARGS(InfoQueue.ReleaseAndGetAddressOf())) DXGI 정보 큐를 받음. 그래픽 도구가 없으면 실패하고, 그때는 디버그 팩토리 없이 그대로 진행함
    • D3D_DRIVER_TYPE_NULL 화면에 그리지 않는 드라이버. 디버그 레이어가 있는지만 보려고 이 드라이버로 디바이스를 먼저 만들어 봄
    • Device.As(&D3DInfoQueue) 디버그 레이어를 켠 디바이스는 ID3D11InfoQueue 도 가짐. SetMuteDebugOutput 으로 D3D11 런타임이 출력 창에 직접 쓰는 것을 끔
    • SetBreakOnSeverity(..., TRUE) 에러와 손상(CORRUPTION) 등급 메시지에서 실행을 멈추게 함. 디버거가 없을 때 멈추면 프로그램이 죽어서 IsDebuggerPresent 로 감쌈
    자세히 · 에러에서 멈추기

    잘못 부른 D3D 함수는 대개 실패 코드를 돌려주지 않고 메시지만 남겨요. 정점 셰이더 없이 그리는 호출이 그런 예예요. 멈추지 않으면 콘솔에 빨간 줄이 찍히고 그림이 이상한 채로 계속 돌아서, 어느 줄이 원인인지 찾기 어려워요.

    디버거가 붙어 있으면 D3D11 이 에러를 알린 호출 안에서 멈춰요. 호출 스택이 그 호출을 가리켜요. 스왑체인을 만들 때 같은 DXGI 쪽 실패는 호출 안에서 멈추지 않고, 뒤따르는 CHECK_FATAL 줄에서 멈춰요.

    멈춘 순간의 메시지 문장은 출력 창에 없어요. D3D11 런타임의 출력을 꺼 두었기 때문이에요. 문장은 FlushDebugMessages 가 콘솔로 옮겨요.

    메시지는 DXGI 정보 큐 하나에서 꺼내요. 스왑체인 메시지는 DXGI 쪽이라 D3D11 의 ID3D11InfoQueue 로는 받지 못해요. 꺼내는 때는 Initialize 끝과 Present 뒤마다예요. Visual Studio 출력 창에는 DXGI 메시지가 두 번 찍혀요. 한 번은 DXGI 런타임이, 한 번은 FLog 가 찍어요.

    줄 단위 풀이
    • GetMessage(DXGI_DEBUG_ALL, Index, nullptr, &Length) 처음에는 길이만 받고, 그만큼 버퍼를 잡은 뒤 다시 불러 내용을 받음
    • CHECK_RETURN(...) 메시지 하나를 못 꺼내는 것은 치명 실패로 볼 일이 없어 함수만 빠져나옴
    • Message->Producer == DXGI_DEBUG_DXGI 메시지를 낸 쪽에 따라 [DXGI]·[D3D] 를 붙임
    • FStringConv::ToWide(Message->pDescription) 메시지 문장은 char 문자열이라 02편의 넓히기 함수로 바꿈

    DXGI_DEBUG_ALL 같은 GUID 는 dxguid.lib 에 들어 있어요. 프로젝트 속성에서 구성을 모든 구성으로 두고 링커 › 입력 › 추가 종속성의 dxgi.lib; 뒤에 dxguid.lib; 를 더해요.

  6. 치명 실패 직전에 원인을 남긴다

    CHECK_FATAL 로 끝날 때도 원인이 로그에 남아야 해요. 5단계의 메시지는 Present 뒤에만 꺼내서, 실패로 곧바로 끝나면 쌓인 메시지가 찍히지 않아요. 치명 실패 때도 내보내려고 ReportFatal 이 로그와 상자보다 먼저 부를 훅을 Check 에 더하고, FD3D11Graphics 가 그 훅에 원인을 남기는 함수를 걸어요.

    줄 단위 풀이
    • const std::function<void()> Hook = std::move(FatalHook); 훅을 꺼내 비운 뒤 부름. 훅 안에서 다시 치명 실패가 나도 훅이 두 번 불리지 않음

    훅에 거는 OnFatal 은 쌓인 디버그 메시지를 내보내고, 디바이스를 잃었으면 그 원인을 찍어요. 드라이버를 갱신하거나 GPU 가 멈췄다 복구되면 디바이스가 제거되고, Present 가 0x887A0005(DXGI_ERROR_DEVICE_REMOVED)로 실패해요. 이 값만으로는 왜 잃었는지 알 수 없어서 GetDeviceRemovedReason 을 물어요. 원인은 릴리스 빌드에서도 필요해서 훅은 빌드 구성과 상관없이 걸어요.

    줄 단위 풀이
    • ::Return::SetFatalHook([this] { OnFatal(); }); 디바이스를 만들기 전에 걸어서 초기화 중의 실패도 덮음. 이때는 Device 가 아직 비어 있어 OnFatal 이 원인을 묻지 않음
    • ::Return::SetFatalHook(nullptr); 훅은 이 객체의 주소를 붙잡고 있음. 복사를 막아 둬서 객체가 옮겨지지 않으니 소멸할 때 한 번만 풀면 됨
    • FAILED(RemovedReason) 디바이스가 멀쩡하면 S_OK. 제거됐으면 DXGI_ERROR_DEVICE_HUNG(GPU 가 멈춤)·DXGI_ERROR_DEVICE_RESET 같은 원인 코드가 옴

    이제 치명 실패로 끝나면 디버그 레이어가 남긴 원인 문장이 [CHECK FATAL] 줄 바로 위에 찍혀요. 흔한 실수 두 항목의 증상이 그 예예요. 디바이스를 잃었다면 그 사이에 장치 제거 원인 줄이 하나 더 찍혀요.

먼저 예측

코드를 보기 전에 답을 하나씩 정해 두세요. 틀려도 돼요. 정해 둔 답이 있으면 코드를 읽다가 그 대목에서 멈추게 돼요.

1 · 창은 언제 파괴될까요

닫기 단추를 누르면 창은 그 순간 파괴될까요? 그렇지 않다면 언제 파괴될까요?

답 보기

누른 순간에는 파괴되지 않아요. 닫기 단추가 보내는 WM_CLOSE 를 받으면 메시지 루프에 끝내라는 신호만 보내고, 창은 루프가 끝난 다음 FWindow 의 소멸자가 DestroyWindow 를 부를 때 파괴돼요. (6단계)

2 · static 함수가 객체를 어떻게 찾을까요

창에 일이 생기면 Windows 는 미리 등록해 둔 함수 하나를 불러요. 이 함수는 this 가 없는 static 함수예요. 어느 객체의 창에서 온 메시지인지는 어떻게 알아낼까요?

답 보기

창마다 포인터 하나를 저장할 수 있는 칸이 있어요. 창을 만들 때 넘긴 this 가 창이 만들어지는 도중에 오는 메시지와 함께 돌아오면, 그 칸에 저장해 두고 이후 메시지마다 꺼내 써요. (3단계)

따라 하기

코드 조각의 배지는 할 일이에요. 새로는 추가, 바꿈은 있던 함수나 파일을 통째로 바꿔 넣기, 지움은 빨간 줄 지우기예요. diff 조각은 초록 줄을 넣고 빨간 줄을 지워요.

  1. 공통 도구 셋을 미리 만들어 둔다

    창을 만들기 전에 도구 세 개를 먼저 넣어요. 03편부터 매 편에 쓰는 것들이고 이 편의 주제는 따로 있으니 이름과 하는 일만 알고 넘어가도 돼요.

    CHECK_RETURN 은 식이 실패하면 그 식과 파일 이름, 줄 번호를 로그에 남기고 함수에서 바로 반환해요. 실패로 치는 값은 false, nullptr, 실패를 뜻하는 HRESULT 예요.

    Win32 개념 · 실패를 알리는 세 가지 방식
    • HRESULT 32비트 결과 코드. 음수면 실패이고 0 이상이면 성공. D3D 에서 객체를 만드는 함수 대부분이 이 형을 돌려줌
    • BOOL·ATOM 같은 정수 : 0 이면 실패. RegisterClassExW 등
    • 핸들과 포인터 : nullptr 이면 실패. CreateWindowExW 등

    실패는 FLog 가 받아 Visual Studio 출력 창과 콘솔 창에 찍어요. 콘솔 창은 디버그 빌드에서만 열려요. FLog 는 TSingleton 을 상속한 싱글톤이고 로그 함수가 static 이라 어디서든 FLog::Info(...) 한 줄로 불러요.

    FLog·TSingleton 코드와 Check.cpp
    줄 단위 풀이
    • L"" #Expression 식을 문자열로 바꾸고 앞의 L"" 와 이어 붙여 와이드 문자열로 만듦
    • return __VA_ARGS__; 반환값 칸. CHECK_RETURN(식) 처럼 비우면 return; 이 되어 void 함수에서도 쓸 수 있음
    • do { ... } while (false) 매크로를 if 와 else 사이에 써도 문장 하나로 묶이게 하는 관용구

  2. 창 클래스를 등록하고 창을 만든다

    Win32 에서 창을 띄우려면 호출이 두 번 필요해요. 창 클래스를 등록하는 호출과 그 클래스 이름으로 창을 만드는 호출이에요. 여기서 클래스는 C++ 의 클래스와 상관없는 Win32 용어라 아래 상자부터 보고 가세요.

    Win32 개념 · 창 클래스와 창
    • 창 클래스(WNDCLASSEXW) : 아이콘·커서·배경색과 메시지를 받을 함수를 묶은 등록 정보. 프로세스 안에서 이름으로 구분
    • 창(HWND) : 등록된 클래스 이름으로 만든 실제 창. HWND 는 그 창을 가리키는 핸들이고 같은 클래스로 여러 개를 만들 수 있음
    • 스타일 : WS_OVERLAPPEDWINDOW 는 제목 표시줄과 테두리가 있고 크기를 바꿀 수 있는 보통 창. WS_POPUP 은 둘 다 없는 창
    • 클라이언트 영역 : 제목 표시줄과 테두리를 뺀 안쪽. 03편부터 여기에 그림
    줄 단위 풀이
    • int Width = 800; 창을 처음 만들 때의 클라이언트 영역 크기. 선언하면서 기본값을 줌
    • bool bFullScreen = false; 전체 화면과 커서 숨김은 이 편에서 켜지 않음. 기본값 그대로 둠
    • FWindow(const FWindow& Other) = delete; 복사를 막으면 이동도 함께 막혀 객체 주소가 바뀌지 않음. 3단계에서 이 주소를 창에 저장하기 때문에 필요. 언리얼의 UE_NONCOPYABLE 도 복사와 이동을 함께 막음
    • FWindow() = default; 복사 생성자를 적으면 컴파일러가 기본 생성자를 만들어 주지 않아서 되살린 것
    • std::function<void(UINT, WPARAM, LPARAM)> MessageCallback; FWindow 가 직접 처리하지 않는 메시지를 넘길 콜백. 받는 쪽이 누구인지 FWindow 는 모름
    • int GetWidth() const { return Width; } 지금의 클라이언트 영역 크기

    FWindow.cpp 는 새 파일이에요. include 묶음 다음에 Initialize 를 넣고, 나머지 함수는 그 함수를 다루는 단계에서 캡션이 말하는 자리에 넣어요.

    800×600 은 창 전체가 아니라 클라이언트 영역의 크기예요. CreateWindowExW 는 제목 표시줄과 테두리를 포함한 바깥 크기를 받기 때문에 Initialize 가 그 차이를 AdjustWindowRect 로 구해 더해요. 배율 100% 에서는 가로 16, 세로 39 픽셀이 더해져 바깥 크기가 816×639 가 돼요.

    줄 단위 풀이
    • constexpr const wchar_t* ClassName 창 클래스 이름이자 창 제목. 이 함수 안에서만 쓰는 값
    • CS_HREDRAW | CS_VREDRAW 가로나 세로 크기가 바뀌면 창 전체를 다시 그림
    • WindowClass.lpfnWndProc = &FWindow::WndProc; 이 클래스로 만든 창의 메시지를 받을 함수. 3단계
    • GetStockObject(BLACK_BRUSH) 배경색. 직접 그리기 전까지 창이 검게 보이는 이유
    • RegisterClassExW(&WindowClass) != 0 돌려주는 ATOM 은 0 이면 실패인 정수라 CHECK_RETURN 이 받지 않음. 성공 조건을 비교식으로 적음
    • DWORD Style = WS_POPUP; 전체 화면의 기본값. 테두리 없는 창을 화면 크기로 만들 뿐이고 해상도는 바꾸지 않음
    • AdjustWindowRect(&Bounds, Style, FALSE); 제목 표시줄과 테두리의 두께는 스타일마다 달라서 Style 을 함께 넘김. 세 번째 인자 FALSE 는 창에 메뉴가 없다는 뜻
    • PositionX = (ScreenWidth - OuterWidth) / 2; 화면 가운데에 놓음
    • CreateWindowExW(..., Instance, this); 마지막 인자는 창이 만들어지는 도중에 WM_NCCREATE 메시지와 함께 돌아옴. 3단계
    • GetClientRect(Handle, &Client); 실제로 만들어진 클라이언트 영역 크기를 다시 읽어 보관
    • ShowWindow(Handle, ShowCmd); wWinMain 이 받은 값을 그대로 넘김. 바로 가기의 "최소화된 채로 시작" 같은 설정을 따르게 됨
    원문과 비교

    원문은 창 모드에서도 WS_POPUP 을 써서 제목 표시줄과 테두리가 없어요. 보통 창으로 바꾸면서 AdjustWindowRect 계산이 새로 들어갔어요. 원문에는 있고 여기에는 없는 호출은 아래와 같아요.

    • CS_OWNDC, WS_CLIPSIBLINGS, WS_CLIPCHILDREN : OpenGL 창에 쓰던 설정
    • ChangeDisplaySettings 와 복원 : 지금 해상도를 그대로 다시 넣는 호출이라 효과가 없음
    • WS_EX_APPWINDOW : 소유자가 없는 최상위 창은 원래 작업 표시줄에 나옴
    • SetForegroundWindow, SetFocus : ShowWindow 로 충분. 마이크로소프트의 DirectXTK 앱 템플릿도 ShowWindow 만 부름
    • UnregisterClass : 프로세스가 끝나면 자동으로 해제. 같은 템플릿도 부르지 않음

  3. static 함수에서 객체를 찾는다

    FWindow::WndProc 는 static 함수라 this 가 없어요. 창에 일이 생기면 Windows 가 앞 단계에서 lpfnWndProc 에 넣은 이 함수를 불러요. 넘겨주는 것은 창 핸들 HWND 와 WM_ 으로 시작하는 메시지 번호, 메시지마다 뜻이 달라지는 값 두 개뿐이라 이것으로 FWindow 객체를 찾아내야 해요.

    이 함수는 static 이어야 해요. Win32 는 C 로 만든 API 라 평범한 함수 포인터만 받는데 멤버 함수는 보이지 않는 인자 this 를 하나 더 받아서 형이 맞지 않아요. static 을 지우고 빌드하면 lpfnWndProc 에 대입하는 줄에서 컴파일 에러가 나요.

    창을 만들 때 창에 딸린 칸에 this 를 넣어 두고 메시지가 올 때마다 꺼내요.

    Win32 개념 · 창에 딸린 저장 공간
    • GWLP_USERDATA 창마다 하나씩 있는 포인터 크기의 칸. 시스템은 쓰지 않음. SetWindowLongPtrW 로 넣고 GetWindowLongPtrW 로 꺼냄
    • WM_NCCREATE 창이 만들어지는 도중에 오는 메시지. CreateWindowExW 의 마지막 인자가 CREATESTRUCTW 의 lpCreateParams 에 담겨 옴
    • DefWindowProcW 직접 처리하지 않는 메시지를 맡기는 기본 처리 함수

    this 는 WM_NCCREATE 에서 넣어요. 앞 단계에서 넘긴 this 가 처음 돌아오는 메시지예요.

    그런데 이 메시지가 첫 메시지는 아니에요. 창의 최소·최대 크기를 묻는 WM_GETMINMAXINFO 가 먼저 와요. 그때 칸에서 꺼낸 값은 아직 nullptr 이라 그 메시지는 DefWindowProcW 에 맡겨요. 이 검사를 빼면 nullptr 로 멤버 함수를 부르게 돼요.

    Run 의 루프는 WM_QUIT 을 꺼내야 끝나요. 그 WM_QUIT 을 누가 넣는지, 루프가 끝난 뒤 창을 누가 파괴하는지가 이 단계예요.

    Win32 개념 · 창이 닫힐 때 오는 메시지
    • WM_CLOSE 닫기 단추나 Alt+F4 를 눌렀을 때. 닫아 달라는 요청일 뿐이고, DefWindowProcW 에 맡기면 그쪽에서 DestroyWindow 를 부름
    • WM_DESTROY 창이 파괴되는 도중에 옴. DestroyWindow 가 보냄
    • WM_ENDSESSION Windows 를 끄거나 로그아웃할 때. 이때는 WM_CLOSE 가 오지 않음
    • PostQuitMessage 큐에 WM_QUIT 을 넣는 함수

    원문은 소멸자에 정리 코드를 두지 않아요. ExitThread() 같은 함수가 소멸자를 부르지 않고 스레드를 끝내 버릴 수 있다는 이유로 정리를 전부 Shutdown() 에 모아 두고 끝날 때 직접 불러요.

    저는 반대로 정했어요. 창을 파괴하는 코드는 FWindow 의 소멸자에만 두고, 끝내자는 신호는 PostQuitMessage 로만 보내요. 그러면 닫기 단추든 ESC 든 모두 Run 이 돌아오는 한 곳으로 모이고 정리도 그 뒤 한 곳에서 끝나요. 이 프로그램에는 ExitThread 를 부르는 곳이 없어서 원문이 걱정한 상황도 생기지 않아요.

    ESC 는 앞 단계의 Update 가 RequestExit 을 불러요. 닫기 단추와 Windows 종료는 4단계에서 친 HandleMessage 의 case WM_CLOSE 와 case WM_ENDSESSION 으로 와요. 세 곳 모두 PostQuitMessage(0) 만 부르고 창은 파괴하지 않아요.

    WM_CLOSE 를 return 0 으로 끝내지 않고 DefWindowProcW 에 넘기면 그쪽에서 창을 곧바로 파괴해요. 파괴하는 길이 소멸자 말고 하나 더 생기는 셈이라 넘기지 않아요.

    다만 Windows 를 끌 때는 WM_ENDSESSION 을 처리하고 돌아온 뒤 정리가 끝나기 전에 프로세스가 끝날 수 있어요. 지금은 저장할 것이 없어서 그대로 둬요.

	case WM_ENDSESSION:
		if (WParam == TRUE)
		{
			PostQuitMessage(0);

	case WM_ENTERSIZEMOVE:

		return 0;

	case WM_EXITSIZEMOVE:
		bSizing = false;

		return 0;

	case WM_SIZE:
		if (WParam != SIZE_MINIMIZED && bSizing == false)
		{
			NotifyResize();
		}

WM_QUIT 은 누가 큐에 넣나요? WndProc 에는 왜 오지 않나요?

답 보기

PostQuitMessage 가 넣어요. 이 편에서는 WM_CLOSE, WM_ENDSESSION, FSystem::RequestExit 세 곳에서 불러요. WM_QUIT 에는 받는 창이 없어요. 스레드의 메시지 큐에만 놓이기 때문에 루프가 꺼낸 메시지를 직접 확인해야 해요.

3

Run 은 메시지를 하나 처리하면 continue 로 돌아가 다음 메시지부터 봐요. 메시지 하나를 처리할 때마다 Frame 도 한 번씩 부르게 바꾸면 무엇이 달라질까요?

답 보기

메시지가 프레임보다 자주 오면 처리가 밀려요. 프레임마다 하나씩만 꺼내서는 큐가 줄지 않아 입력이 점점 늦게 반영돼요. 큐를 다 비운 뒤에 프레임을 돌면 그 프레임은 가장 최근 입력 상태에서 시작해요. 02편은 Frame 이 비어 있어 이 차이가 드러나지 않아요.

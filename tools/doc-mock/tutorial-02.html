wWinMain 이 창을 만든 직후 곧바로 돌아오면 그 창은 어떻게 될까요?

답 보기

wWinMain 이 돌아오면 프로세스가 끝나고 창도 함께 파괴돼요. 창을 띄워 두려면 wWinMain 이 돌아오지 않고 메시지 루프를 돌며 끝내라는 신호를 기다려야 해요. (2단계)

2 · static 함수가 객체를 어떻게 찾을까요

창에 일이 생기면 Windows 는 미리 등록해 둔 함수 하나를 불러요. 이 함수는 this 가 없는 static 함수예요. 어느 객체의 창에서 온 메시지인지는 어떻게 알아낼까요?

답 보기

창마다 포인터 하나를 저장할 수 있는 칸이 있어요. 창을 만들 때 넘긴 this 가 창이 만들어지는 도중에 오는 메시지와 함께 돌아오면, 그 칸에 저장해 두고 이후 메시지마다 꺼내 써요. (3단계)

따라 하기

코드 조각 위의 경로는 리포 루트 기준이에요. 새 파일은 그 폴더에 만들어요. Visual Studio 의 새 항목 추가는 기본 위치가 프로젝트 파일 옆이라 위치를 그 폴더로 바꿔야 해요. 배지는 할 일이에요. 신규는 새 파일이나 새 함수를 넣기, 수정은 있던 것을 고치기, 삭제는 지우기예요. 통째로 보이는 조각은 그대로 넣거나 바꿔 넣고, diff 조각은 초록 줄을 넣고 빨간 줄을 지워요. 단계마다 끝의 여기까지 상자대로 빌드하고 실행해 보세요.

  1. 공통 도구 셋을 미리 만들어 둔다

    창을 만들기 전에 도구 세 개를 먼저 넣어요. 2단계부터 쓰고 뒤 편에서도 계속 써요. 이 편의 주제는 따로 있으니 하는 일만 알고 넘어가도 돼요.

    • CHECK_*실패를 검사함. CHECK_RETURN 은 로그를 남기고 함수에서 돌아가고, CHECK_FATAL 은 그 줄에서 멈춤
    • TSingleton프로그램에 하나뿐인 객체의 틀. 처음 Get() 할 때 만들어지고, Prepare·Release 로 만들고 없앨 때를 정할 수 있음
    • FLogVisual Studio 출력 창과 콘솔 창에 로그를 찍음. 콘솔 창은 디버그 빌드에서만 열림

    다섯 파일은 모두 Source/Utility 에 새로 만들어요.

    CHECK_RETURN 은 식이 실패하면 그 식과 파일 이름, 줄 번호를 로그에 남기고 함수에서 바로 반환해요. 실패로 치는 값은 false, nullptr, 실패를 뜻하는 HRESULT 예요.

    창을 만들지 못한 것처럼 계속할 수 없는 실패는 CHECK_FATAL 이 그 줄에서 멈춰요. 디버거로 실행 중이면 __debugbreak 에서 먼저 멈춰서 호출 스택과 변수를 실패한 순간 그대로 볼 수 있어요. 디버거가 없으면 로그를 남기고 실패한 식과 줄 번호를 상자로 띄운 뒤 종료 코드 1 로 끝나요.

    Win32 개념 · 실패를 알리는 세 가지 방식
    • HRESULT 32비트 결과 코드. 음수면 실패이고 0 이상이면 성공. D3D 에서 객체를 만드는 함수 대부분이 이 형을 돌려줌
    • BOOL·ATOM 같은 정수 : 0 이면 실패. RegisterClassExW 등
    • 핸들과 포인터 : nullptr 이면 실패. CreateWindowExW 등
    줄 단위 풀이
    • L"" #Expression 식을 문자열로 바꾸고 앞의 L"" 와 이어 붙여 와이드 문자열로 만듦
    • const auto CheckResult = (Expression); 식을 한 번만 계산해 판정과 로그에 같이 씀
    • return __VA_ARGS__; 반환값 칸. CHECK_RETURN(식) 처럼 비우면 return; 이 되어 void 함수에서도 쓸 수 있음
    • do { ... } while (false) 매크로를 if 와 else 사이에 써도 문장 하나로 묶이게 하는 관용구
    • ::Return::Succeeded(CheckResult) HRESULT·bool·포인터만 받는 오버로드 셋. 0 이 성공인 HRESULT 와 0 이 실패인 정수가 섞이지 않도록 BOOL 과 ATOM 에는 맞는 오버로드를 두지 않음
    • std::wstring Describe(HRESULT Result); 결과가 HRESULT 면 HRESULT 0x887A0001 처럼 값을 로그에 붙임. bool 과 포인터는 붙일 것이 없어 빈 문자열
    • [[noreturn]] void ReportFatal(...) 돌아오지 않는 함수. 컴파일러도 이 호출 뒤로는 실행이 이어지지 않는다고 봄
    줄 단위 풀이
    • template <typename T> class TSingleton 싱글톤으로 만들 클래스가 자기 자신을 T 로 넘겨 상속함. class FLog : public TSingleton<FLog>
    • static std::unique_ptr<T> Instance; 하나뿐인 객체. 프로그램이 끝날 때 함께 해제됨
    • static void Release() 해제할 때를 코드에서 정할 때만 부름. 부른 뒤에 Get() 이 오면 경고와 함께 다시 만들어짐
    • TSingleton() = default; protected 라서 상속한 클래스만 만들 수 있음

    FLog 는 TSingleton 을 상속한 싱글톤이에요. 로그 함수가 static 이라 어디서든 FLog::Info(...) 한 줄로 불러요.

    줄 단위 풀이
    • static void Info(std::wstring_view Message); wstring_view 는 문자열을 복사하지 않고 주소와 길이만 받음. 실제 출력은 FLog.cpp 의 OutputDebugStringW 와 WriteConsoleW. W 로 끝나는 함수라 한글이 깨지지 않음
    • namespace { ... } 이름 없는 네임스페이스. 안의 변수와 함수는 이 파일에서만 보임
    • MB_TASKMODAL 부모 창을 넘기지 않아도 상자가 떠 있는 동안 이 스레드의 창이 입력을 받지 않음
    • std::_Exit(1) 표준 함수. exit 와 달리 atexit 로 등록한 함수도 부르지 않음

    Visual Studio 에서는 솔루션 탐색기에 Utility 필터를 만들고 새 .h·.cpp 를 기존 항목 추가로 넣어요. Main.cpp 는 필터에 넣지 않고 그대로 둬요. 프로젝트 속성은 아래 둘을 고쳐요. 이 조작들이 DxRenderDojo.vcxproj 와 DxRenderDojo.vcxproj.filters 를 바꿔요.

    • 모든 구성 · C/C++ › 일반 › 추가 포함 디렉터리 : $(ProjectDir)Source. #include "Utility/Check.h" 처럼 Source/ 기준으로 폴더까지 적을 수 있게 함
    • Debug·Release 각각 · C/C++ › 전처리기 › 전처리기 정의 : WIN32_LEAN_AND_MEAN 추가. Windows.h 가 잘 쓰지 않는 헤더를 빼고 읽게 함
    참고 : 위 조작이 프로젝트 파일에 남기는 diff · 따로 치지 않음
    CMake · 맥 빌드와 검사용, VS 만 쓰면 건너뜀

    CMake 는 Source/ 아래의 .cpp 를 모두 모아 빌드하니 새 파일은 적지 않아요. 프로젝트 속성에서 고친 두 값만 옮겨요.

    여기까지

    빌드하면 경고 없이 끝나요. 도구를 부르는 코드가 아직 없어서 실행하면 곧바로 끝나요.

  2. 창을 만들고 메시지 루프를 돌린다

    창을 띄우려면 Win32 호출이 두 번 필요하고, 띄운 뒤에는 wWinMain 이 돌아오지 않고 메시지를 꺼내며 기다려야 해요. 먼저 창 클래스를 등록하고 그 클래스 이름으로 창을 만들어요. 여기서 클래스는 C++ 의 클래스와 상관없는 Win32 용어라 아래 상자부터 보고 가세요.

    Win32 개념 · 창 클래스와 창
    • 창 클래스(WNDCLASSEXW) : 아이콘·커서·배경색과 메시지를 받을 함수를 묶은 등록 정보. 프로세스 안에서 이름으로 구분
    • 창(HWND) : 등록된 클래스 이름으로 만든 실제 창. HWND 는 그 창을 가리키는 핸들이고 같은 클래스로 여러 개를 만들 수 있음
    • 스타일 : WS_OVERLAPPEDWINDOW 는 제목 표시줄과 테두리가 있고 크기를 바꿀 수 있는 보통 창. WS_POPUP 은 둘 다 없는 창
    • 클라이언트 영역 : 제목 표시줄과 테두리를 뺀 안쪽. 03편부터 여기에 그림
    줄 단위 풀이
    • int Width = 800; 창을 처음 만들 때의 클라이언트 영역 크기. 선언하면서 기본값을 줌
    • bool bFullScreen = false; 시작할 때 전체 화면으로 띄울지와 커서를 숨길지. 이 편은 둘 다 false 그대로 둠
    • FWindow(const FWindow& Other) = delete; 복사를 막으면 이동도 함께 막혀 객체 주소가 바뀌지 않음. 3단계에서 이 주소를 창에 저장하기 때문에 필요. 언리얼의 UE_NONCOPYABLE 도 복사와 이동을 함께 막음
    • FWindow() = default; 복사 생성자를 적으면 컴파일러가 기본 생성자를 만들어 주지 않아서 되살린 것
    • int GetWidth() const { return Width; } 지금의 클라이언트 영역 크기

    FWindow.cpp 는 새 파일이에요. 창 클래스에는 메시지를 받을 함수가 있어야 해서 WndProc 도 함께 넣어요. 지금은 모든 메시지를 기본 처리 함수 DefWindowProcW 에 넘기기만 해요.

    800×600 은 창 전체가 아니라 클라이언트 영역의 크기예요. CreateWindowExW 는 제목 표시줄과 테두리를 포함한 바깥 크기를 받기 때문에 Initialize 가 그 차이를 AdjustWindowRect 로 구해 더해요. 배율 100% 에서는 가로 16, 세로 39 픽셀이 더해져 바깥 크기가 816×639 가 돼요.

    줄 단위 풀이
    • constexpr const wchar_t* ClassName 창 클래스 이름이자 창 제목. 이 함수 안에서만 쓰는 값
    • CS_HREDRAW | CS_VREDRAW 가로나 세로 크기가 바뀌면 창 전체를 다시 그림
    • WindowClass.lpfnWndProc = &FWindow::WndProc; 이 클래스로 만든 창의 메시지를 받을 함수
    • GetStockObject(BLACK_BRUSH) 배경색. 직접 그리기 전까지 창이 검게 보이는 이유
    • RegisterClassExW(&WindowClass) != 0 돌려주는 ATOM 은 0 이면 실패인 정수라 CHECK_FATAL 이 받지 않음. 성공 조건을 비교식으로 적음
    • DWORD Style = WS_POPUP; 전체 화면의 기본값. 테두리 없는 창을 화면 크기로 만들 뿐이고 해상도는 바꾸지 않음
    • AdjustWindowRect(&Bounds, Style, FALSE); 제목 표시줄과 테두리의 두께는 스타일마다 달라서 Style 을 함께 넘김. 세 번째 인자 FALSE 는 창에 메뉴가 없다는 뜻
    • PositionX = (ScreenWidth - OuterWidth) / 2; 화면 가운데에 놓음
    • CreateWindowExW(..., Instance, this); 마지막 인자는 창이 만들어지는 도중에 WM_NCCREATE 메시지와 함께 돌아옴. 3단계
    • CHECK_FATAL(Handle); 창을 만들지 못하면 더 할 일이 없어서 그 줄에서 멈춤
    • GetClientRect(Handle, &Client); 실제로 만들어진 클라이언트 영역 크기를 다시 읽어 보관

  3. static 함수에서 객체를 찾는다

    닫기를 제대로 처리하려면 창의 메시지를 FWindow 의 멤버 함수에서 받아야 해요. 그런데 FWindow::WndProc 는 static 함수라 this 가 없어요. Windows 가 넘겨주는 것은 창 핸들 HWND 와 WM_ 으로 시작하는 메시지 번호, 메시지마다 뜻이 달라지는 값 두 개뿐이라 이것으로 FWindow 객체를 찾아내야 해요.

    이 함수는 static 이어야 해요. Win32 는 C 로 만든 API 라 평범한 함수 포인터만 받는데 멤버 함수는 보이지 않는 인자 this 를 하나 더 받아서 형이 맞지 않아요. static 을 지우고 빌드하면 lpfnWndProc 에 대입하는 줄에서 컴파일 에러가 나요.

    • DefWindowProcW 직접 처리하지 않는 메시지를 맡기는 기본 처리 함수

    Win32 개념 · 창이 닫힐 때 오는 메시지
    • WM_CLOSE 닫기 단추나 Alt+F4 를 눌렀을 때. 닫아 달라는 요청일 뿐이고, DefWindowProcW 에 맡기면 그쪽에서 DestroyWindow 를 부름
    • WM_DESTROY 창이 파괴되는 도중에 옴. DestroyWindow 가 보냄
    • WM_ENDSESSION Windows 를 끄거나 로그아웃할 때. 이때는 WM_CLOSE 가 오지 않음
    • PostQuitMessage 큐에 WM_QUIT 을 넣는 함수

    원문은 소멸자에 정리 코드를 두지 않아요. ExitThread() 같은 함수가 소멸자를 부르지 않고 스레드를 끝내 버릴 수 있다는 이유로 정리를 전부 Shutdown() 에 모아 두고 끝날 때 직접 불러요.

    저는 반대로 정했어요. 창을 파괴하는 코드는 FWindow 의 소멸자에만 두고, 끝내자는 신호는 PostQuitMessage 로만 보내요. 그러면 닫기 단추든 Windows 종료든 모두 Run 이 돌아오는 한 곳으로 모이고 정리도 그 뒤 한 곳에서 끝나요. 이 프로그램에는 ExitThread 를 부르는 곳이 없어서 원문이 걱정한 상황도 생기지 않아요.

    닫기 단추와 Windows 종료는 case WM_CLOSE 와 case WM_ENDSESSION 으로 와요. 둘 다 PostQuitMessage(0) 만 부르고 창은 파괴하지 않아요.

	case WM_EXITSIZEMOVE:

		}

		}

WndProc 가 GWLP_USERDATA 에서 꺼낸 포인터는 nullptr 일 때가 있어요. 언제이고 왜 그런가요?

답 보기

창이 만들어지는 도중, WM_NCCREATE 가 오기 전까지예요. 주소는 WM_NCCREATE 에서 저장하는데 WM_GETMINMAXINFO 가 그보다 먼저 와요. 그 구간의 메시지는 DefWindowProcW 에 맡겨요.

2

WM_QUIT 은 누가 큐에 넣나요? WndProc 에는 왜 오지 않나요?

답 보기

PostQuitMessage 가 넣어요. 이 편에서는 WM_CLOSE, WM_ENDSESSION, FSystem::RequestExit 세 곳에서 불러요. WM_QUIT 에는 받는 창이 없어요. 스레드의 메시지 큐에만 놓이기 때문에 루프가 꺼낸 메시지를 직접 확인해야 해요.

3

Run 은 메시지를 하나 처리하면 continue 로 돌아가 다음 메시지부터 봐요. 메시지 하나를 처리할 때마다 Frame 도 한 번씩 부르게 바꾸면 무엇이 달라질까요?

답 보기

메시지가 프레임보다 자주 오면 처리가 밀려요. 프레임마다 하나씩만 꺼내서는 큐가 줄지 않아 입력이 점점 늦게 반영돼요. 큐를 다 비운 뒤에 프레임을 돌면 그 프레임은 가장 최근 입력 상태에서 시작해요. 02편은 Frame 이 비어 있어 이 차이가 드러나지 않아요.

1. 설정과 입력 : FDisplaySettings, FInput

    창 크기·전체 화면 설정과 키 상태를 담을 작은 타입 두 개를 만듭니다.

    왜 필요한가

    원문은 FULL_SCREEN, VSYNC_ENABLED 같은 상수를 applicationclass.h 전역에 둡니다.
    전역 상수는 어느 파일에서든 읽을 수 있어서, 값이 어디서 쓰이는지 따라가기 어렵습니다.
    그래서 설정을 구조체로 묶고, 쓰는 클래스인 FSystem 이 멤버로 들고 있게 합니다.

    • int Width = 800; : 멤버를 선언하면서 바로 기본값을 줍니다. 생성자에서 값을 넣을 필요가 없습니다
    • bFullScreen : bool 변수라 b 접두를 붙입니다
    • std::array<bool, 256> Keys = {}; : 가상 키 코드(0~255)마다 눌림 여부를 담습니다. = {} 로 전부 false 가 됩니다
    • IsKeyDown : 한 줄 게터라 헤더에 인라인 const 로 둡니다
    • FInput() = default; : 바로 아래에서 복사를 막으면 컴파일러가 기본 생성자를 만들지 않으므로 되살립니다

    원문과 비교

    원문 InputClass 는 bool m_keys[256] 배열을 Initialize 에서 반복문으로 false 로 채웁니다.
    헤더의 초기화 한 줄이 그 일을 대신합니다.

    언리얼로 치면

    FDisplaySettings 는 UGameUserSettings 가 들고 있는 해상도·전체 화면 설정의 아주 작은 버전입니다.
    FInput 은 UPlayerInput 이 키 상태를 추적하는 일을 가장 단순하게 줄인 것입니다.

  2. 실패 검사 : CHECK_RETURN

    실패하면 로그를 남기고 바로 반환하는 매크로를 만듭니다.

    왜 필요한가

    Win32 와 D3D 함수는 대부분 실패를 반환값으로 알립니다.
    매번 if 문으로 확인하면 코드가 길어지고, 로그를 빠뜨리기 쉽습니다.

    Win32 개념 · 실패를 알리는 방식

    • HRESULT : 32비트 결과 코드. 최상위 비트가 1 이면 실패라 음수로 읽힘. D3D 함수 대부분
    • BOOL·ATOM : 0 이면 실패. RegisterClassExW 등
    • 핸들(HWND 등) : nullptr 이면 실패. CreateWindowExW 등
    • Succeeded 오버로드 세 개 : 넘긴 값의 타입에 따라 판정 방식을 고릅니다
    • BOOL·ATOM 을 그대로 넘기면 : 딱 맞는 오버로드가 없어 컴파일 에러가 납니다. 0 이 성공인 정수를 실수로 성공 처리하지 않게 하려는 것입니다
    • ReportFailure : 실패한 식·파일·줄 번호를 OutputDebugStringA 로 Visual Studio 출력 창에 남깁니다
    • #Expression : 식을 문자열로 바꿔 로그에 그대로 찍습니다
    • __VA_ARGS__ : 반환값 자리. CHECK_RETURN(식) 처럼 비우면 return; 이 되어 void 함수에서도 씁니다
    • do { ... } while (false) : 매크로가 if·else 사이에서도 문장 하나처럼 동작하게 하는 관용구입니다

    언리얼로 치면

    if (!ensureMsgf(식, ...)) { return false; } 를 한 줄로 줄인 것에 가깝습니다.
    ensure 처럼 로그를 남기고 프로그램을 멈추지 않지만, 콜스택은 남기지 않고 그 자리에서 반환합니다.
    실패하면 멈추는 check 와는 다릅니다.

  3. 누가 무엇을 들고 있나 : FSystem 선언

    창과 메시지 루프를 맡는 FSystem 의 모양을 정합니다.

    왜 필요한가

    누가 무엇을 만들고 지우는지가 헤더에 드러나면, 이후 편에서 클래스가 늘어나도 수명을 따라가기 쉽습니다.

    • static ... WndProc : 창 메시지를 받는 함수입니다. static 멤버라 규약대로 맨 위에 둡니다. 왜 static 이어야 하는지는 5단계에서 봅니다
    • FSystem(const FSystem &Other) = delete; : 복사를 막습니다. 창에 이 객체의 주소를 저장하므로, 복사본이 생기면 창이 엉뚱한 객체를 가리킵니다
    • FSystem() = default; : 복사 생성자를 선언하면 컴파일러가 기본 생성자를 만들지 않으므로 되살립니다
    • ~FSystem(); : 창·창 클래스·해상도는 스마트 포인터가 정리하지 못해 소멸자에서 돌려놓습니다
    • ApplicationName : 창 클래스 이름과 창 제목으로 함께 씁니다
    • Instance, Window : 이 exe 와 만든 창을 가리키는 핸들
    • Input, Application : unique_ptr 로 소유합니다. FSystem 이 지워질 때 함께 지워집니다

    언리얼로 치면

    FSystem 은 FEngineLoop 자리입니다.
    Initialize 가 PreInit·Init 에, Run 이 매 프레임 Tick 을 부르는 바깥 루프에 해당합니다.
    std::unique_ptr 는 TUniquePtr 이고, 복사를 막는 두 줄은 UE_NONCOPYABLE 매크로가 하는 일과 비슷합니다.

  4. 창 만들기 : Initialize

    창 클래스를 등록하고, 그 클래스로 창을 하나 만듭니다.

    Win32 개념 · 창 클래스와 창

    창 클래스는 "이 창들은 메시지를 이 함수로 보내고, 커서와 배경은 이것을 쓴다" 같은 공통 설정에 이름을 붙여 OS 에 등록한 것입니다.
    창은 CreateWindowExW 에 그 이름을 넘겨서 만듭니다.
    같은 클래스로 창을 여러 개 만들 수 있습니다.

    • std::make_unique : 입력과 앱 객체를 먼저 만듭니다. 창이 생기는 순간부터 메시지가 들어오기 때문입니다
    • GetModuleHandleW(nullptr) : 지금 실행 중인 exe 의 인스턴스 핸들입니다. WinMain 이 받는 Instance 와 같은 값입니다
    • CS_HREDRAW | CS_VREDRAW : 창 크기가 바뀌면 전체를 다시 그립니다
    • CS_OWNDC : 창마다 전용 그리기 컨텍스트(DC)를 둡니다
    • lpfnWndProc : 이 클래스의 창이 받는 메시지를 넘길 함수입니다
    • hbrBackground : 창 배경을 칠할 브러시. 검은색입니다
    • RegisterClassExW(...) != 0 : ATOM 을 돌려주고 0 이면 실패라 비교식으로 넘깁니다
    • 창 모드 : 화면 크기에서 창 크기를 빼고 반으로 나눠 가운데 위치를 구합니다
    • 전체 화면 : ChangeDisplaySettingsW 로 해상도를 바꾸고, 창 크기를 화면 크기에 맞춥니다. 02편 기본값은 창 모드입니다
    • WS_EX_APPWINDOW : 작업 표시줄에 버튼을 표시합니다
    • WS_POPUP : 제목 표시줄과 테두리가 없는 창입니다
    • WS_CLIPSIBLINGS | WS_CLIPCHILDREN : 겹친 형제 창과 자식 창의 영역에는 그리지 않습니다
    • 부모 창·메뉴 자리의 nullptr : 최상위 창이고 메뉴가 없습니다
    • 마지막 인자 this : 창을 만드는 동안 WM_NCCREATE 메시지에 실려 돌아옵니다. 다음 단계에서 이 값을 씁니다
    • ShowCursor(FALSE) : 커서 표시 카운터를 하나 줄여 이 창 위에서 커서를 숨깁니다. 소멸자의 ShowCursor(TRUE) 와 짝입니다

    원문과 비교

    원문은 이 코드를 InitializeWindows 로 따로 뺍니다.
    규약상 Initialize 가 직접 일하므로 한 함수에 둡니다.

    언리얼로 치면

    FWindowsWindow::Initialize 가 같은 일을 합니다.
    창 스타일을 고르고 CreateWindowEx 로 창을 만듭니다.

  5. 메시지를 객체로 보내기 : WndProc, HandleMessage

    OS 가 부르는 static 함수에서, 이 창을 만든 FSystem 객체를 찾아 멤버 함수로 넘깁니다.

    Win32 개념 · 창 프로시저와 메시지

    키 입력이나 창 닫기 같은 사건은 메시지(WM_KEYDOWN, WM_CLOSE 등)로 전달됩니다.
    메시지를 받는 함수가 창 프로시저이고, 창 클래스를 등록할 때 지정합니다.
    메시지마다 뜻이 다른 값 두 개가 WPARAM·LPARAM 으로 따라옵니다. WM_KEYDOWN 이면 WPARAM 이 가상 키 코드(VK_ESCAPE 등)입니다.

    왜 static 이어야 하나

    OS 는 창 프로시저를 일반 함수로 부르므로 this 를 넘겨주지 않습니다.
    그래서 멤버 함수를 바로 지정할 수 없고, static 함수가 먼저 받아 객체를 찾아야 합니다.

    • WM_NCCREATE : 창을 만드는 도중, CreateWindowExW 가 돌아오기 전에 오는 메시지입니다. LParam 이 CREATESTRUCTW 를 가리키고, 그 lpCreateParams 가 CreateWindowExW 에 넘긴 this 입니다
    • SetWindowLongPtrW(..., GWLP_USERDATA, ...) : 창마다 앱이 자유롭게 쓰는 칸 하나에 주소를 저장합니다
    • GetWindowLongPtrW : 이후 메시지마다 그 주소를 꺼냅니다
    • System == nullptr : WM_NCCREATE 보다 먼저 오는 메시지가 있습니다. 그때는 저장한 주소가 없으므로 기본 처리 DefWindowProcW 로 넘깁니다
    • WM_KEYDOWN·WM_KEYUP : 키 상태를 FInput 에 기록합니다
    • WM_CLOSE·WM_DESTROY : PostQuitMessage(0) 으로 메시지 큐에 종료 신호 WM_QUIT 을 넣습니다
    • DefWindowProcW : 직접 처리하지 않는 메시지는 OS 기본 동작(창 이동, 크기 조절 등)에 맡깁니다

    원문과 비교

    원문은 전역 포인터 ApplicationHandle 에 객체 주소를 넣고, 창 프로시저에서 꺼냅니다.
    이 리포는 전역을 두지 않으므로 창 자체에 저장합니다.

    언리얼로 치면

    FWindowsApplication::AppWndProc 가 static 창 프로시저이고, 받은 메시지를 ProcessMessage 멤버 함수로 넘깁니다. 구조가 같습니다.
    언리얼은 앱 객체가 하나뿐이라 원문처럼 전역 포인터로 객체를 찾습니다.

  6. 메시지 루프와 종료 : Run, Frame, 소멸자

    메시지를 처리하면서 매 프레임 일을 하고, 끝나면 OS 자원을 돌려놓습니다.

    Win32 개념 · 메시지 큐와 PeekMessage

    OS 는 스레드마다 메시지 큐를 두고 키 입력 같은 메시지를 쌓습니다.
    GetMessageW 는 메시지가 올 때까지 기다리므로, 입력이 없으면 프레임도 멈춥니다.
    PeekMessageW 는 메시지가 없으면 바로 돌아오므로 그 틈에 프레임을 돌 수 있습니다. 게임 루프가 PeekMessageW 를 쓰는 이유입니다.

    • PM_REMOVE : 꺼낸 메시지를 큐에서 지웁니다
    • TranslateMessage : 키 입력 메시지에서 문자 입력 메시지(WM_CHAR)를 만들어 큐에 더합니다
    • DispatchMessageW : 메시지를 그 창의 창 프로시저로 보냅니다
    • continue : 큐가 빌 때까지 메시지부터 처리하고, 비면 Frame 을 돕니다
    • Message.message != WM_QUIT : PostQuitMessage 가 넣은 종료 신호를 꺼내면 루프가 끝납니다
    • Frame : ESC 가 눌렸으면 false 로 루프를 끝내고, 아니면 FApplication::Frame 에 맡깁니다. 02편에서는 늘 true 이고, 03편부터 여기서 그립니다
    • ShowCursor(TRUE) : 숨겼던 커서를 되돌립니다
    • ChangeDisplaySettingsW(nullptr, 0) : 전체 화면으로 바꿨던 해상도를 원래대로 돌립니다
    • DestroyWindow, UnregisterClassW : 만든 순서의 반대로 창과 창 클래스를 정리합니다

    원문과 비교

    원문은 프레임마다 메시지를 하나만 처리합니다.
    메시지가 몰리면 입력 반영이 늦어질 수 있어, 쌓인 메시지를 먼저 비우도록 바꿨습니다.

    언리얼로 치면

    FWindowsPlatformApplicationMisc::PumpMessages 가 같은 PeekMessage 루프로 메시지를 비웁니다.
    Run 의 바깥 루프는 GuardedMain 에서 IsEngineExitRequested() 가 참이 될 때까지 매 프레임 EngineTick 을 부르는 부분에 해당합니다.

  7. WinMain 과 빌드 등록

    WinMain 에서 FSystem 을 만들어 돌리고, 새 소스를 두 빌드에 등록합니다.

    • std::make_unique<FSystem>() : 규약상 new 를 직접 쓰지 않습니다
    • CHECK_RETURN(System->Initialize(), 1) : 초기화에 실패하면 종료 코드 1 로 끝냅니다
    • WinMain 이 끝나면 System 이 지워지면서 소멸자가 불립니다
    • WIN32 : 콘솔이 아닌 창 프로그램(/SUBSYSTEM:WINDOWS)으로 링크합니다
    • target_include_directories(... Source) : #include "Core/FSystem.h" 처럼 Source/ 기준 경로로 include 합니다
    • WIN32_LEAN_AND_MEAN : Windows.h 에서 잘 쓰지 않는 헤더(암호화, RPC, 셸 등)를 빼서 컴파일을 가볍게 합니다. 원문은 헤더에서 #define 합니다
    • DxRenderDojo.vcxproj 에도 같은 내용이 들어갔습니다. 아래 "바뀐 파일" 의 diff 에서 확인합니다

    언리얼로 치면

    언리얼은 UBT 가 모듈 폴더의 소스를 알아서 모읍니다.
    이 리포는 빌드가 두 벌이라 새 파일을 직접 등록합니다.
